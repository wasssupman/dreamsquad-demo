# 에이전트 운용 · 검증 · 이식 감사

리드 1 + 구현·리뷰 에이전트 여럿이 한 워크트리·한 에디터를 나눠 쓸 때 겪은 것. 출처는 대부분 `battle-core-rebuild`(2026-09-22~25, `docs/spec/battle-core-rebuild/handoff_session_2026-09-24.md` 함정 1~30)다. git 인덱스 공유는 `02-dev-workflow-git-scene.md` 「병행 세션 커밋 위생」, 에디터 세션은 `01-unity-mcp-operation.md` 를 본다.

## 에이전트의 「N/N 통과」는 리드가 export 로 다시 돌린다

구현 에이전트의 통과 보고는 그 에이전트의 작업 트리 기준이다. 남의 dirty 파일, 커밋 안 된 수정, 스테일 어셈블리가 섞여도 초록이 나온다.

- **처방**: 보고된 커밋 SHA 를 `git archive <sha> <경로들> | tar -x -C <scratch>` 로 클린 export 해 리드가 build · test · Check 를 재실행한다(명령 전문은 `docs/spec/battle-core-rebuild/handoff_session_2026-09-24.md` §5). 수치가 보고와 같을 때만 다음 단계로.
- 테스트 총계가 기대만큼 안 늘었으면 새 테스트가 **안 돈 것**이다(헤드리스 lane 에서 신규 `.cs` 가 csproj 에 안 잡히면 빌드가 1초 만에 「오류 0」으로 끝난다 — 그 짧은 빌드 시간이 신호다).

## 계획 리뷰는 내용만이 아니라 top-down 으로도 공격한다

battle-core-rebuild 초안은 내용 리뷰만 통과시켰다가 **씬 · 브랜치 · 동결 훅 · 테스트 lane** 이 통째로 빠진 것이 완전성 리뷰(13건)에서 드러났다.

- **처방**: spec 초안마다 격리 critic 을 붙이되, 「이 계획을 실행하려면 무엇이 먼저 있어야 하나」(환경·도구·검증 경로)를 따로 묻는다.

## 리뷰어도 틀린다 — 지적은 코드로 대조한 뒤 반영한다

리뷰어가 `using Wassup.Battle.Units` 를 죽은 import 로 **두 번** 지적했다(5c · 7e). 당시 `Faction` 열거형은 Skills asmdef 안에 있었지만 namespace 는 그 이름이었다 — 반영했으면 컴파일이 깨졌다. 폴더·asmdef 이름으로 네임스페이스를 추정한 오판이다(unit 9 이후 `Faction` 은 namespace `Somnia.Battle.Skills`).

- **처방**: 지적마다 해당 `파일:줄` 을 리드가 열어 본다. 반복된 오판은 리뷰어 정의(`.claude/agents/*.md`)에 적어 막는다.

## 구현 에이전트는 옛 규칙을 조용히 바꿔 놓는다

「개체당 1회」를 「칸 1회 소비」로 읽어 효과 타일이 첫 배치에 사라졌다(6b). 5b 는 라이브 기능 둘(탭 선택 배치 · 패널 퇴근 버튼)을 「은퇴」로 오판하고 새 조작을 지었다.

- **처방**: 보고의 「주의할 점」에 규칙 차이가 나오면 옛 코드 줄로 확정하고 **옛 규칙으로 되돌리는 것이 기본**이다(사용자 결정이 있을 때만 예외). 「이식 제외」의 제거·은퇴에는 **옛 spec 인용**이 있어야 한다.
- 반대 방향도 있다 — 죽은 기제를 살리라고 잘못 지시한 사례. 데이터가 그 분기를 **실제로 타는지**까지 본다.

## 옛 테스트를 새 코드로 옮기는 작업이 곧 규칙 누락 감사다

unit 9 가 옛 테스트 33 파일을 코어로 이식하다 옛 규칙과의 차이 6건을 찾았다. 조각 C·D 에서 옛 테스트 짝 지도를 먼저 만들었으면 그때 잡혔다.

- **처방**: 재작성·이식 spec 은 **초기에** 「옛 테스트 → 새 규칙 위치」 짝 지도를 만든다. 짝 없는 옛 테스트는 규칙 공백 후보다.

## 장부의 「새 주인」 칸은 심볼로 쓰고 기계로 존재를 검사한다

battle-core-rebuild 장부는 미정 0 이었지만, 「새 주인」 칸에 적힌 이름 중 **코드에 실체가 없는 것이 12행** 남아 있었다(`--owners` 검사가 찾음). 사람 눈에는 배정이 끝난 것처럼 보였다.

- **처방**: 이관 장부의 담당 칸은 첫 백틱 심볼 + 별칭표 문법으로 쓰고, 스크립트가 그 심볼의 존재를 확인한다. 「배정 완료」와 「실현 완료」를 따로 센다.
- 같은 결: 컴포넌트가 씬 배선 없이 `FindAnyObjectByType` 폴백 + 경고로 돌게 지으면 테스트가 배선 없이 초록이다. 배선 전에 「미배선」 표(GUID 포함)를 spec 에 남긴다.

## 「지울 수 있다」의 증명은 지울 패키지의 dll 까지 빼고 돌린다

8c `Retire.Check` 는 퇴역 파일을 export 에서 지우고 컴파일해 오류 0 을 냈다. 그러나 참조 dll 집합에 **지울 Entities 패키지가 남아 있어** 그 패키지에 기대는 파일 7개를 못 잡았다. unit 9 에서 패키지를 빼자 드러났다.

- **처방**: 삭제 증명은 삭제 대상 소스 **와** 제거할 패키지 어셈블리를 둘 다 뺀 상태로 컴파일한다. 음성 대조(남아야 할 파일 하나를 지우면 오류가 나는지)로 검사 자체가 살아 있는지 확인한다.

## 삭제 커밋에서 남는 쪽을 지키던 테스트 그물을 같이 지우지 말 것

unit 9 가 옛 전투를 지우며 제약 13(판정 산식) 위반을 막던 아키텍처 테스트도 같이 지웠다. 그 사이에 코어의 포탈 판정이 표기 전용 상수를 판정에 쓰는 위반이 살아 있었다(감사 후속 `95f91b8c6` 로 수정 + 코어판 그물).

- **처방**: 그물(아키텍처·금지 패턴 테스트)을 지우는 커밋에는 **남는 코드용 그물**을 같이 넣는다. 그물의 대상 경로만 바꾸면 되는 경우가 많다.

## 에디터는 한 번에 한 에이전트 — 반납은 보고가 아니라 상태로 확인한다

리드가 「Unity 보류」를 지시했는데 에이전트가 `refresh_unity` 를 걸었다. 다른 에이전트가 「에디터 반납」을 보고한 뒤에도 테스트 러너가 돌고 `isPlaying` 이 참이었다. 둘이 겹치면 러너가 고착되거나 사용자 Play 가 끊긴다.

- **처방**: 에디터 사용권은 리드가 한 에이전트에만 넘긴다. 넘기기 전에 `editor_state` 의 `isPlaying`·테스트 러너 상태를 직접 확인한다(CLAUDE.md 「Unity 함정」).

## 지시는 상대의 마지막 보고 시각을 보고 낸다

리드가 「미커밋으로 두라」고 보낸 시점에 에이전트는 이미 커밋한 뒤였다. 메시지가 엇갈렸다.

- **처방**: 지시 전에 상대의 마지막 보고와 `git log` 를 확인한다. 결과가 이력상 초록이면 되돌리지 않고 그 위에서 잇는다.

## 브랜치·main 양쪽에서 spec 이 갱신되면 감사가 stale 본을 읽는다

구현 에이전트가 브랜치 커밋에 spec 갱신을 넣는 동안 main 워크트리의 spec 은 옛 본이었고, main 에서 돈 감사가 그것을 읽고 오판했다.

- **처방**: unit 종료마다 브랜치의 spec 폴더를 main 에 동기화(`git checkout <branch> -- docs/spec/<slug>` 후 docs 커밋)하거나, 감사를 브랜치 워크트리에서 돌린다.
