## 0. 이 프로젝트의 현재 단계

이 프로젝트의 초기 단계는 **"기획의 프로토타입"**이다. 즉, 기획의 핵심 가설들을 최소한의 플레이 가능한 형태로 구현해서 검증하는 것이 목적이다. 다만 **코드 자체는 일회용이 아니다** — 초기 단계의 구현이 검증을 통과하면 그대로 본 게임의 기반으로 이어진다. 이 문서는 "초기 수직 슬라이스"의 스코프와 품질 기준을 정의한다.

### 운영 원칙

- **기능 스코프는 프로토타입 수준**: 현재 Phase 범위를 넘는 기능은 만들지 않는다.
- **코드 품질은 본 게임 수준**: 만든 코드는 버려질 것으로 취급하지 않는다. 단, "본 게임에서 쓸 수 있게 예쁘게"를 이유로 과도한 추상화를 쌓지 않는다.
- **맥락별 분리**: 전투 시뮬레이션은 처음부터 맥락(Units / Combat / Movement / Effects)별로 나누어 작성한다. 상세는 TRD 섹션 2.5 참조.
- **확장 여지만 열고 실 구현은 현재 Phase만**: 다음 Phase에서 추가될 시스템의 "자리"는 열어두되, 해당 Phase 진입 전까지 구현하지 않는다.

### 검증 가설

- **H1 (드래프트 판단 학습 신호)**: 플레이어는 반복 플레이를 통해 드래프트 픽 선택이 개선된다. 즉, 동일 공격 패턴에 대해 반복 플레이할 때 픽 결정이 점점 더 "상위 플레이어의 픽"에 수렴한다.
- **H2 (3분 루프의 긴장감)**: 코스트 제약 하에서의 배치 + 스킬 사용 결정이 플레이어에게 "지금 쓸까 아낄까"의 실시간 긴장감을 준다.
- **H3 (패배 원인의 귀인 가능성)**: 플레이어는 패배 후 "내가 무엇을 잘못했는지"를 구체적으로 언어화할 수 있다. ("모르겠다, 운이 나빴다"가 아닌 구체적 판단 실수 지목.)
- **H4 (아키텍처 타당성)**: 하이브리드 ECS + BattleBridge 단일 창구 + 맥락별 분리가 이 규모의 디펜스 게임에 맞는 선택인가. Phase 경계에서 누적 리뷰를 통해 검증된다.

세 가설 중 **H1이 실패하면 기획 전면 재검토**다. H2/H3는 튜닝 여지가 있다. H4는 누적 경험으로 판단한다.

### 명시적 비목표 (현재 Phase 기준)

다음은 Phase 0에 포함되지 않는다. 이 목록은 Phase가 진행되면서 점진적으로 줄어든다.

- 비동기 세션 / 병행 토너먼트 / 정산 / 20~30분 타이머
- 에고 유닛 / 별자리 / 트리 / 개인화
- 컬렉션덱 5슬롯 / 아웃게임 가중치 관리
- 시즌 메타 교체 / 환경 효과의 시즌별 변화
- 가챠 / 수집 / 시즌 패스 / BM / 재화 순환
- 튜토리얼 / 온보딩 / 단계 해금
- 멀티플레이어 네트워킹 (봇 상대만)
- 푸시 알림 / 계정 시스템 / 로그인
- 스킨 / 꾸미기 / D&D 특수 모션
- 카메라 회전 (고정 Low-TopDown 유지)

## 1. 프로토타입 스코프

### 1.1 기술 스택 / 아키텍처

> **기술 스택, ECS 경계, 금지 패턴, 폴더 구조, Phase 순서는 본 문서에서 다루지 않는다. `TRD.md`를 참조하라.**
>
> 요약: Unity 6 + Entities 6.x + 하이브리드 ECS (전투만 ECS, 나머지 MonoBehaviour) + Android 타겟. `BattleBridge`가 경계의 유일한 통신 창구.

### 1.2 플레이 범위 (수직 슬라이스)

한 판의 흐름은 다음과 같다.

```
[판 시작] → [공격 타임라인 확인 화면] → [드래프트 픽 (10종 중 7종)]
→ [초기 배치 페이즈] → [실시간 방어 3분] → [판 결과 화면]
```

**판 외부의 모든 것은 빠진다**. 타이틀 화면, 메인 메뉴, 토너먼트 선택, 세션 구조 — 전부 없다. 빌드를 실행하면 바로 판이 시작되거나, 최소한의 "시작" 버튼 하나에서 바로 판으로 진입한다.

### 1.3 포함 시스템

| 시스템 | 범위 | 목적 |
|---|---|---|
| 공격 타임라인 | 판 시작 전 적 유닛 등장 순서 사전 공개 | H1: 드래프트 판단의 근거 제공 |
| 드래프트 | 10종 풀에서 7종 픽 | H1 검증 |
| 초기 배치 | 20×10 복셀 그리드, 타일당 1종 (A안) | H2 |
| 코스트 시스템 | 최대 10, 초기 지급 + 주기 충전 + 특수 유닛 처치 보너스 | H2 |
| 실시간 방어 | 3분 타이머, 배치/스킬 실시간 결정 | H2 |
| 스킬 | 2종 고정 (유틸성) | H2 |
| 적 유닛 (봇/더미) | 타임라인 기반 자동 진행, AI 없음 | 공격 패턴 제공 |
| 스코어 | 판 결과 화면에 표시 (정산은 없음) | H1 반복 측정 |
| 로컬 로깅 | 드래프트 픽/배치/스킬 사용/스코어 JSON 기록 | H1/H3 측정 도구 |

### 1.4 제외 시스템 (중요)

프로토타입 제작 중 "이것도 넣으면 좋겠다"는 유혹이 반복해서 올 것이다. 다음은 **들어오지 않는다**:

- 세션 시스템, 정산, 병행 토너먼트, 타이머 대기
- 에고, 별자리, 트리
- 컬렉션덱, 가중치 조절, 아웃게임 관리
- 시즌 교체, 환경 효과의 시즌 변화
- 가챠, BM, 재화, 시즌 패스, 티켓
- 계정, 로그인, 네트워킹, 푸시
- 튜토리얼, 온보딩, 해금
- 스킨, 꾸미기, 카메라 회전
- 봇의 지능형 드래프트/배치 (프로토타입의 봇은 단순 더미)

"나중에 쉽게 넣을 수 있도록 훅만 둔다"도 금지한다. 프로토타입 단계에서는 훅이 설계 오염이다. 필요할 때 리팩토링한다.

## 2. 시스템 상세 스펙

### 2.1 공격 타임라인

- 각 판은 **시즌 룰 없이 고정된 3~5개의 공격 패턴** 중 하나가 선택된다. 프로토타입 기간 동안 같은 플레이어가 같은 패턴을 여러 번 반복 플레이할 수 있어야 한다 (H1 측정 요건).
- 타임라인은 적 유닛 종류, 등장 시간(초 단위), 진입 경로를 포함한다.
- 판 시작 전 플레이어에게 **전체 타임라인이 공개**된다. "3:00에 탱커 3기 등장" 같은 수준의 정보.
- 타임라인 확인 화면은 단순해도 되지만 **읽을 수 있어야 한다** — H1의 학습 신호는 여기서부터 시작된다.

**공격 패턴 3~5종의 내용** (프로토타입용 예시):
1. **탱커 웨이브**: 체력 높은 탱커 다수가 순차 진입
2. **원거리 딜러 후열**: 탱커 앞에 원거리 딜러가 뒤에 배치된 복합 웨이브
3. **스웜**: 낮은 체력의 다수 적이 빠르게 밀려옴
4. **혼합**: 위 세 가지의 혼합
5. **(선택)**: 보스형 단일 고체력 적

### 2.2 드래프트

- **풀 10종**이 판 시작 시 노출된다.
- 플레이어는 10종 중 **7종을 픽**한다. 픽 순서는 자유, 픽 후 되돌리기 가능.
- 프로토타입 단계의 풀은 **공용 기본 유닛 풀 한 세트(10~12종)에서 매 판 랜덤 10종 추출**한다. 기본덱/메타 픽/컬렉션덱의 구분은 없다. 공정성 수학은 프로토타입에서 검증 대상이 아니다.
- 드래프트 UI는 각 유닛의 특성(공격/인접 시너지)을 **읽을 수 있어야 한다**. 툴팁 수준이어도 됨.

### 2.3 유닛 (방어)

- 프로토타입 기간 동안 **10~12종의 방어 유닛**을 만든다.
- 각 유닛은:
  - 기본 스탯: 공격력, 체력, 공격속도, 사거리
  - 배치 시 효과 1종 (즉시 발동)
  - 인접 시너지 1종 (옆 유닛 종류에 따라 스탯 증가)
- 시너지는 **읽기 쉬워야 한다**. "이 유닛과 저 유닛이 붙으면 공격력 +20%" 수준의 단순 규칙.

### 2.4 유닛 (공격)

- 프로토타입 기간 동안 **5~7종의 공격 유닛**을 만든다.
- 탱커, 일반 딜러, 원거리 딜러, 빠른 스웜, 특수 유닛 등 최소 역할 구분이 가능할 것.
- AI는 단순 경로 따라가기. 의사결정 없음.

### 2.5 배치

- **20×10 복셀 그리드** 고정 사용.
- 일부 타일은 적의 이동 경로, 일부는 배치 타일, 일부는 장애물. 맵 한 장을 고정하여 프로토타입 내내 재사용.
- **A안**: 타일당 1종 배치. 배치 후 위치 고정. 이동 불가.
- 초기 배치 페이즈에서 드래프트한 7종 중 **최대 7슬롯까지** 배치. 초기 코스트 안에서 가능한 만큼.

### 2.6 코스트

- **최대 10**, 초기 지급 3~5 (튜닝), 주기 충전 (N초당 1), 특수 유닛 처치 시 +1 보너스.
- 각 유닛 배치 / 스킬 사용에 코스트 소모.
- 실제 수치는 프로토타입 플레이 테스트로 튜닝한다.

### 2.7 실시간 방어 (3분)

- 타이머 3:00 시작, 타임라인대로 적이 등장.
- 플레이어는 실시간으로 **(a) 새 유닛 추가 배치** 또는 **(b) 스킬 사용**.
- 종료 조건:
  - 적 전멸: 즉시 승리, 남은 시간이 스코어에 가산
  - 시간 초과: 남은 적 체력 총합으로 스코어 계산
  - 적 N마리 이상 진입 허용: 패배

### 2.8 스킬 (2종)

프로토타입 기간 동안 다음 2종을 구현한다. 시즌/랜덤 선택 없이 **두 스킬이 매 판 모두 사용 가능**하다.

- **토네이도**: 지정 위치 3x3 범위에 N초간 적 이동 방해. 코스트 3.
- **포탈**: 입구/출구 2개 배치, 적이 입구 진입 시 출구로 강제 이동. 각 설치 코스트 2 (총 4).

### 2.9 봇 상대 (더미 수준)

프로토타입에서 "봇 상대"는 **같은 공격 패턴을 방어하는 가상의 다른 플레이어**를 의미한다. 프로토타입에서는 이 봇이 **미리 기록된 고정 스코어 5개**를 반환할 뿐이다. 지능 없음, AI 없음. 목적은 결과 화면에서 "내 스코어 vs 다른 참가자 스코어"를 보여주는 UI 훈련장일 뿐.

### 2.10 결과 화면

판 종료 시 다음을 표시한다:
- 내 스코어
- 5명 봇의 더미 스코어와의 비교 (내 순위)
- 내가 픽한 7종과 배치 위치 요약
- "다시 시작" 버튼 (같은 공격 패턴을 반복 플레이 가능)
- "다른 패턴으로" 버튼

**H1 측정 핵심**: "다시 시작"이 있어야 반복 플레이의 픽 개선이 측정 가능하다.

### 2.11 로깅 (H1/H3 측정 도구)

로컬 파일에 JSON으로 다음을 기록한다. 네트워크 전송 없음, 로컬만.

```json
{
  "session_id": "...",
  "timestamp": "...",
  "attack_pattern_id": "...",
  "draft": { "pool": [...], "picked": [...] },
  "placement": [ {"unit": "...", "tile": [x,y]} ],
  "skill_uses": [ {"skill": "...", "time": ..., "position": [x,y]} ],
  "result": { "score": ..., "outcome": "win/lose/timeout" }
}
```

이 로그가 H1 검증의 유일한 정량 데이터 소스다. 로그 없이는 프로토타입의 가치가 반감된다.

## 3. 비주얼 / 아트

### 3.1 수준

프로토타입은 **"기능이 읽히는 최소한의 비주얼"**을 목표로 한다. 미적 품질은 검증 대상이 아니다.

- 유닛: 색깔 다른 스프라이트 또는 Primitive 메쉬로 충분. 종류 구분만 되면 됨.
- 맵: 회색 타일 + 경로 강조 색 + 배치 가능 타일 색 구분
- UI: Unity UGUI 기본 컴포넌트, 폰트/컬러 최소화
- 카메라: 고정 Low-TopDown, 회전 없음, 줌 없음 (또는 최소)

### 3.2 카메라 회전 결정

상세 문서에서 "프로토타입 초기에 결정"으로 지정된 항목. 본 프로토타입에서는 **카메라 회전 없음**으로 확정한다. 이유는:
- 회전을 허용하면 빌보드 시인성 검증이 필요해져 스코프 증가
- 회전의 부재가 검증 가설 3종 중 어느 것에도 불리하지 않음
- 회전 필요성 여부는 H1~H3 검증 이후 재검토

## 4. 검증 프로토콜

### 4.1 H1 측정

**데이터 수집**: 3~5명 플레이어가 각자 동일한 공격 패턴을 **최소 10회** 반복 플레이. 로그 자동 수집.

**분석**:
- 첫 3회와 마지막 3회의 **픽 유사도** (Jaccard 유사도 등)
- 첫 3회와 마지막 3회의 **평균 스코어** 차이
- 픽 선택이 "고성능 픽"에 수렴하는지 (플레이어 간 비교)

**통과 기준**: 마지막 3회의 평균 스코어가 첫 3회 대비 의미 있게 높고, 픽 분포가 수렴 경향을 보일 것.

### 4.2 H2 측정

**데이터 수집**: 플레이 직후 30초 설문 3문항.
- "3분 동안 코스트를 언제 쓸지 고민이 됐다" (5점 척도)
- "배치 vs 스킬 선택이 의미 있었다" (5점 척도)
- "3분이 지루했다/부족했다/적절했다"

**통과 기준**: 4점 이상 응답이 다수.

### 4.3 H3 측정

**데이터 수집**: 패배 직후 짧은 인터뷰 (1~2분).
- "방금 왜 졌나요?" (오픈 질문)
- 답변을 "구체적 판단 지목" vs "모호함/운"으로 코딩

**통과 기준**: 구체적 지목이 전체 답변의 60% 이상.

### 4.4 테스트 규모

- 최소 5명, 권장 8~10명
- 팀 내부 + 외부 지인 혼합
- 사전 게임 설명 **최소화** (읽히는지 자체가 검증 대상)

## 5. 개발 단계 (Phase 구분)

> **Phase 순서와 각 Phase 요약은 `TRD.md` 섹션 6을 참조**. 각 Phase의 상세는 `PHASE{N}.md` 문서에 있다.
>
> 요약: **Phase 0 (실시간 디펜스 루프) → Phase 1 (드래프트) → Phase 2 (스킬) → Phase 3 (배치/인접 효과) → Phase 4 (마무리)**. 가장 근본적인 재미부터 파생적인 시스템까지의 순서이며, 앞 Phase가 실패하면 뒷 Phase는 무의미하다.

**Phase 진행 원칙**: 각 Phase의 이동 기준은 **종료 조건의 이진 통과**이며, 시간 기반 판단을 하지 않는다. 주관 평가 게이트가 실패하면 다음 Phase로 가지 않고 현재 Phase를 재조정한다.

## 7. 성공 기준 / 실패 기준

### 성공

- H1이 통과: 프로토타입 성공. 다음 단계로 진행.
- H2가 통과: 3분 루프 재미가 있다는 신호. 코스트/스킬 튜닝 방향 확정.
- H3가 통과: 패배 귀인이 가능하다는 신호. 본 게임 설계의 핵심 가설 1개가 검증됨.

### 실패

- H1 실패 → **프로젝트 재검토**. 드래프트 구조가 학습 신호를 만들지 못한다는 뜻이며, 본 게임의 "수직 성장 없는 장기 동기"가 불가능해진다.
- H2 실패 → 코스트/스킬 밸런스 또는 맵 디자인 재설계.
- H3 실패 → 복합 상태 공간의 귀인 가능성을 더 낮추는 방향으로 시스템을 축소해야 할 수 있음 (예: 스킬 제거, 시너지 단순화).

**부분 실패는 정상이다.** 프로토타입은 세 가설을 모두 통과시키기 위한 도구가 아니라, **무엇이 맞고 무엇이 틀렸는지**를 확정하기 위한 도구다.

## 부록 A — 검증 실패 시 대응

프로토타입의 목적은 검증이지 성공이 아니다. 실패 시 대응 경로는 아래와 같다.

### H1 실패 시

학습 신호가 없다는 것은 드래프트가 "무작위" 혹은 "정답 고정"이라는 뜻이다. 대응:
1. 픽의 결과 차이가 실제로 있는지 헤드리스 시뮬레이션으로 검증
2. 유닛 간 트레이드오프가 명확한지 재검토
3. 공격 패턴이 "어느 픽으로도 동일하게 클리어됨" 상태인지 검증
4. 위 모든 것이 OK인데도 실패라면, **드래프트 기반 비동기 경쟁 디펜스라는 설계 자체의 재검토**

### H2 실패 시

코스트 긴장감이 부족하다는 뜻. 대응:
1. 초기 코스트 축소, 충전 속도 저하
2. 스킬 코스트 상향
3. 배치 가능 슬롯 축소

### H3 실패 시

플레이어가 복합 상태 공간을 해석하지 못한다는 뜻. 대응:
1. 결과 화면에 "결정적 순간" 자동 표시 (가장 적이 많이 통과한 웨이브 등)
2. 로그 기반의 간단한 리플레이
3. 시스템 단순화 (스킬 제거 등)
