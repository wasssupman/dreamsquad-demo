# 코덱스로 하네스하기

> 이 문서는 "Codex를 똑똑한 답변기"가 아니라 "반복 가능한 작업 하네스"로 쓰기 위한 운영 문서다. 목적은 한 번 잘 되는 데모가 아니라, 같은 팀과 같은 저장소에서 계속 재현되는 작업 흐름을 만드는 것이다.

---

## 1. 한 줄 정의

**코덱스로 하네스하기**란, Codex에게 "코드를 대신 치게 하는 것"이 아니라 **명확한 제약, 문서, 작업 단위, 검증 루프를 가진 실행 환경**을 제공해 안정적으로 생산성을 끌어내는 방식이다.

즉, 성능은 모델 자체보다도 아래 항목에 더 크게 좌우된다:

- 어떤 문서가 항상 컨텍스트에 들어가는가
- 어떤 결정을 에이전트가 자율적으로 해도 되는가
- 어떤 경우에는 멈추고 질문해야 하는가
- 작업을 어떤 크기로 쪼개는가
- 변경 후 무엇으로 검증하는가

---

## 2. 왜 하네스가 필요한가

Codex는 코드를 쓸 수 있지만, 기본 상태에서는 다음 문제가 반복된다.

- 범위를 넓게 해석해서 지금 필요 없는 구조를 만든다
- 저장소의 로컬 규칙보다 일반적인 모범 사례를 우선한다
- 한 번에 너무 많은 파일을 건드린다
- "돌아갈 것 같은 코드"를 쓰고 검증은 약하게 끝낸다
- 이전 대화에서 이미 정한 제약을 새 세션에서 잃어버린다

하네스는 이 문제를 줄인다. 좋은 하네스는 에이전트를 더 똑똑하게 만들지 않는다. 대신 **실수할 공간을 줄이고, 맞아야 하는 방향을 좁힌다.**

---

## 3. 하네스의 핵심 구성요소

### 3.1 고정 컨텍스트 문서

세션마다 항상 참조해야 하는 기준 문서가 필요하다.

- `CLAUDE.md` 또는 동등한 세션 컨텍스트 문서
- 제품 목적과 검증 기준 문서
- 기술 제약 문서
- 현재 단계별 작업 문서

이 저장소에서는 이미 그 역할이 나뉘어 있다:

- `CLAUDE.md`: 프로젝트 정체성, 현재 단계, 절대 제약
- `docs/PRD.md`: 왜 만드는가, 무엇을 검증하는가
- `docs/TRD.md`: 기술 경계와 금지 패턴
- `docs/PHASE0.md`~`docs/PHASE5.md`: 현재 작업 범위

핵심은 "문서가 많다"가 아니라, **문서마다 역할이 겹치지 않게 분리되어 있어야 한다**는 점이다.

### 3.2 자율 결정 범위

에이전트가 매번 질문하면 속도가 죽고, 반대로 다 자율로 두면 방향이 흔들린다. 그래서 문서에는 다음이 분명해야 한다.

- 에이전트가 혼자 정해도 되는 것
- 애매하면 참조할 우선 문서
- 멈추고 사용자에게 물어봐야 하는 결정

이 저장소의 Phase 문서와 `CLAUDE.md`는 이미 그 패턴을 갖고 있다. 이런 식의 규칙이 하네스의 핵심이다.

### 3.3 작업 단위

하네스는 큰 목표를 직접 처리하지 않는다. 항상 **검증 가능한 작은 작업**으로 쪼갠다.

좋은 작업 단위의 조건:

- 완료/미완료가 분명하다
- 변경 파일 범위가 작다
- 검증 방법이 바로 나온다
- 실패 시 되돌릴 비용이 작다

예:

- 나쁨: "전투 시스템 전체 개선"
- 좋음: "ProjectileHitSystem의 명중 판정 경로를 수정하고 EditMode 테스트 1개 추가"

### 3.4 검증 루프

Codex는 작성보다 검증이 더 중요하다. 하네스는 "무엇을 만들지"보다 "어떻게 통과시킬지"를 먼저 정해야 한다.

검증 수단 예시:

- 단위 테스트
- 통합 테스트
- 빌드/컴파일 확인
- 콘솔 에러 확인
- 수동 플레이 체크리스트
- 스냅샷 비교

검증이 문서화되어 있지 않으면, 에이전트는 대체로 "대충 맞아 보이는 상태"에서 멈춘다.

---

## 4. Codex 하네스 운영 원칙

### 4.1 프롬프트보다 저장소가 우선이다

좋은 하네스는 매 세션 장문의 지시를 다시 쓰지 않는다. 대신 저장소 안에 규칙을 둔다.

- 컨텍스트는 문서에 둔다
- 반복 규칙은 문서나 스크립트에 둔다
- 실행 순서는 작업 문서에 둔다
- 검증 명령은 스크립트나 테스트로 둔다

즉, 프롬프트는 점점 짧아져야 한다. "다음 작업"이라고만 말해도 움직일 수 있어야 하네스가 성숙한 상태다.

### 4.2 추상화는 미래가 아니라 현재 수요로 결정한다

에이전트는 인터페이스, 베이스 클래스, 범용 유틸을 과하게 만드는 경향이 있다. 하네스는 이를 막아야 한다.

운영 기준:

- 구현체가 하나면 인터페이스를 만들지 않는다
- 현재 Phase 밖의 확장은 자리만 열고 구현하지 않는다
- 재사용성이 아니라 현재 작업의 단순성을 우선한다

### 4.3 수정 범위를 강하게 제한한다

한 번에 많은 파일을 바꾸면 검증 비용이 올라가고, 사용자 신뢰가 떨어진다.

권장 규칙:

- 한 작업은 한 목적만 가진다
- 핵심 파일 몇 개만 수정한다
- 문서 업데이트가 필요하면 작업 종료 시점에 함께 한다
- 관련 없는 리팩터링은 금지한다

### 4.4 항상 "검증 가능한 종료 조건"으로 닫는다

작업의 종료는 "코드 작성 완료"가 아니라 아래 둘 중 하나여야 한다.

- 자동 검증이 통과했다
- 사용자가 에디터/앱에서 확인할 구체적 절차가 제시됐다

---

## 5. 실전 루프

Codex를 하네스로 쓸 때는 아래 루프를 반복하면 된다.

### 5.1 루프 1: 방향 고정

세션 시작 시 확인할 것:

1. 현재 Phase는 무엇인가
2. 이번 작업의 단일 목표는 무엇인가
3. 절대 건드리면 안 되는 경계는 무엇인가
4. 완료를 어떤 방식으로 검증할 것인가

### 5.2 루프 2: 컨텍스트 수집

에이전트는 곧바로 쓰기보다 먼저 읽어야 한다.

- 관련 문서
- 관련 코드
- 테스트 위치
- 기존 패턴

이 단계의 목적은 "해결책 찾기"가 아니라 **로컬 규칙 찾기**다.

### 5.3 루프 3: 최소 변경 구현

구현 단계에서는 다음만 지킨다.

- 현재 작업에 필요한 범위만 수정
- 기존 패턴을 우선 재사용
- 불필요한 일반화 금지
- 검증 코드를 함께 추가

### 5.4 루프 4: 검증

가능하면 자동 검증을 먼저 돌린다.

- 테스트
- 컴파일
- 린트
- 에디터 콘솔 점검

자동 검증이 부족한 영역은 수동 확인 절차를 짧고 구체적으로 남긴다.

### 5.5 루프 5: 결과 기록

좋은 하네스는 세션이 끝날수록 더 좋아진다. 그래서 결과를 남긴다.

- 어떤 결정을 했는가
- 왜 그렇게 했는가
- 다음에 같은 상황이 오면 무엇을 따르면 되는가

이 저장소의 `phase*-decisions.md`가 바로 그런 누적 장치다.

---

## 6. 이 저장소에 적용하면 좋은 Codex 하네스 패턴

### 6.1 문서 진입점 고정

Codex가 작업을 시작할 때 우선 읽어야 할 기본 순서는 아래처럼 고정하는 것이 좋다.

1. `CLAUDE.md`
2. 현재 Phase 문서
3. `docs/TRD.md`
4. 필요 시 `docs/PRD.md`

이 순서를 고정하면 "기술적으로는 맞지만 현재 단계와 안 맞는 구현"이 줄어든다.

### 6.2 작업 호출어를 짧게 유지

하네스가 잘 잡히면 사용자 호출은 짧아질 수 있다.

예:

- `다음 작업`
- `P0-07 시작`
- `이 테스트 깨지는 이유 확인`
- `문서 먼저 쓰고 구현은 보류`

짧은 호출이 가능하다는 것은, 저장소 안의 규칙이 충분히 강하다는 뜻이다.

### 6.3 결정 로그를 자산으로 취급

에이전트가 자율 결정한 내용은 잊히기 쉽다. 따라서 다음이 중요하다.

- 결정은 짧게 기록
- 중복 설명은 줄임
- 다음 세션에서 참고 가능한 문장으로 남김

이건 문서화 비용이 아니라, **다음 세션 토큰 비용을 줄이는 작업**이다.

### 6.4 "지금은 안 한다"를 강하게 유지

특히 이 프로젝트처럼 Phase 기반 개발을 할 때는, Codex가 잘하는 것보다 안 하게 만드는 것이 더 중요하다.

막아야 할 것:

- 다음 Phase 기능 선구현
- 아직 쓰지 않는 추상화
- 네트워크, 툴링, 아키텍처 확장
- 시야 밖 리팩터링

---

## 7. 안 좋은 하네스의 징후

아래가 자주 보이면 하네스가 약한 상태다.

- 같은 설명을 세션마다 반복한다
- 에이전트가 매번 폴더 구조를 새로 해석한다
- 작업 단위가 너무 커서 리뷰가 어렵다
- 검증 없이 "완료"가 선언된다
- 사용자가 의도보다 결과물을 더 많이 통제해야 한다
- 문서보다 대화가 더 많은 규칙을 담고 있다

이 경우 모델을 바꾸기 전에 하네스를 고쳐야 한다.

---

## 8. 좋은 하네스의 징후

- 사용자 요청이 짧아도 방향이 흔들리지 않는다
- 수정 범위가 작고 예측 가능하다
- 문서, 코드, 테스트가 같은 제약을 가리킨다
- 에이전트가 로컬 패턴을 먼저 따른다
- 완료 후 검증 방식이 항상 남는다
- 세션이 누적될수록 더 적은 말로 더 정확하게 움직인다

---

## 9. 바로 적용할 수 있는 최소 체크리스트

Codex를 프로젝트 하네스로 쓰려면 최소한 아래 다섯 개는 갖추는 것이 좋다.

1. 세션 시작 시 반드시 읽는 컨텍스트 문서 1개
2. 제품 목적/검증 기준 문서 1개
3. 기술 제약 문서 1개
4. 현재 작업 순서를 가진 문서 1개
5. 변경 후 실행할 검증 루프 1개 이상

이 다섯 개가 없으면, Codex는 매번 새 사람처럼 일한다.

---

## 10. 결론

코덱스로 하네스하기의 본질은 모델 활용이 아니라 **작업 시스템 설계**다.

좋은 하네스는 다음 상태를 만든다:

- 요청은 짧아진다
- 수정은 작아진다
- 검증은 강해진다
- 기록은 누적된다
- 세션 품질이 사람 기억력에 덜 의존하게 된다

이 프로젝트는 이미 그 기반이 있다. `CLAUDE.md`, `TRD`, `PHASE`, `decisions` 문서를 중심으로 작업 호출, 검증, 기록을 더 엄격하게 묶으면 Codex는 단순한 코드 생성기가 아니라 **재현 가능한 개발 하네스의 실행기**로 쓸 수 있다.
