# Phase 0 — 실시간 디펜스 루프

> 본 문서는 `PROTOTYPE_PRD.md`를 전제로 작성되었다. PRD의 스코프·원칙·금지 패턴·ECS 경계 규칙(섹션 1.1.1, 6.x)은 본 문서에서 반복하지 않으며, 본 문서는 **Phase 0의 What과 Done만 정의**한다. How(기술적 설계·클래스 구조·테스트 구성)는 에이전트 구현 재량에 일임한다.

---

## 0. Phase 0의 존재 이유

### 검증 목표

> **"이 게임의 실시간 디펜스 루프가 재미있는가, 최소한 작동하는가"**

Phase 0는 드래프트도, 스킬도, 인접 시너지도 없는 **가장 헐벗은 실시간 디펜스 상태**를 만든다. 이 상태에서 플레이어가 "유닛이 밀려오고, 내가 배치하고, 막혀나가는" 감각을 받는지 본다. 받으면 이 게임의 근본 재미가 존재한다는 뜻이고, 안 받으면 나머지 Phase가 의미 없다.

본 Phase는 PRD의 검증 가설 H1/H2/H3 중 **H2(코스트·배치 결정의 실시간 긴장감)와 H3(패배의 자기 귀인)**을 선제 검증하는 의미도 있다. H1(드래프트 학습 신호)은 Phase 1(드래프트 도입) 이후 검증 대상이다.

### Phase 0가 하는 것 / 안 하는 것

**Phase 0가 하는 것:**
- 정해진 타임라인에 따라 공격 유닛이 경로를 따라 종점까지 이동
- D&D 제스처로 배치 타일에 터치/마우스가 도달하면 **랜덤한 방어 유닛**이 배치됨
- 방어 유닛이 공격 유닛을 자동 공격
- 경로 끝에 공격 유닛 N마리 도달 시 패배
- 공격 유닛 전멸 시 승리
- 승패 결과를 화면에 표시 + 로그 파일에 남김

**Phase 0가 하지 않는 것:**
- 드래프트 (Phase 1)
- 스킬 (Phase 2)
- 배치 시 효과 / 인접 시너지 (Phase 3)
- 코스트 시스템 (Phase 4 또는 그 이후로 유보)
- 유닛 종류 선택 (랜덤 배치)
- UI 장식, 결과 화면 화려함, 통계 패널
- 튜토리얼, 설정, 사운드
- 모바일 특화 최적화 (다만 Android 빌드는 동작해야 함)

**주의**: "배치 시 랜덤"은 Phase 1에서 "드래프트한 7종 중 사용자가 고른 것"으로 교체된다. 지금 랜덤으로 두는 이유는 Phase 0의 검증 목표가 "실시간 루프 자체"이지 "선택 결정"이 아니기 때문이다.

## 1. Phase 0의 게임 흐름

플레이어가 빌드를 실행하면 다음이 일어난다. 메인 메뉴, 토너먼트 선택, 드래프트 UI는 **없다**.

```
[빌드 실행]
  ↓
[맵 + 경로 + 배치 타일 표시]
  ↓
[시작 버튼 또는 자동 시작 — 판단은 에이전트 재량]
  ↓
[타임라인에 따라 공격 유닛이 경로 시작점에 등장]
  ↓
[플레이어는 배치 타일을 터치/드래그하여 방어 유닛 배치]
  ↓
[방어 유닛은 자동으로 사거리 내 공격 유닛 공격]
  ↓
[공격 유닛은 경로 따라 종점 이동, 이동 중 공격받으면 체력 감소, 0 이하 시 소멸]
  ↓
[종점 도달 N마리 ⇒ 패배 / 공격 유닛 전멸 ⇒ 승리]
  ↓
[결과 화면 (최소: "VICTORY" / "DEFEAT" 텍스트 + "다시" 버튼)]
```

## 2. Phase 0 콘텐츠 스펙

### 2.1 맵

- **20×10 복셀 그리드** (PRD 섹션 2.5 준수)
- 타일 종류 3가지: **경로 타일 / 배치 가능 타일 / 장애물 타일**
- 맵 구성은 고정 1장. 프로토타입 내내 이 맵 한 장을 재사용한다.

### 2.2 경로

**2~3개 경로**를 가진다. 경로의 성격은 각각 명확히 구분되어야 한다:

- **경로 A — 직선**: 가장 단순한 경로. 디버깅과 기본 동작 검증용
- **경로 B — 곡선 또는 L자**: 방향 전환이 있는 경로. 유닛의 경로 따라가기 로직 검증
- **경로 C — 분기 또는 우회** (선택): 다른 방식의 경로. 둘로 충분하면 생략 가능

각 경로는 시작점(등장 지점)과 종점(패배 지점)을 가진다. 경로 간 교차 여부는 에이전트가 맵 디자인상 편한 쪽을 선택한다.

### 2.3 공격 유닛 (2~3종)

각 유닛은 기본 스탯을 가진다: **체력 / 이동 속도 / (단순) 공격력**. 이 단계에서 공격 유닛의 공격 행동은 "경로 따라가기"일 뿐이며 방어 유닛을 공격하지 않는다 — 방어 유닛이 일방적으로 공격 유닛을 처리한다. (이 단방향성은 Phase 0의 단순성을 위한 것이며 이후 Phase에서 바뀔 수 있음.)

**유닛 A — 탱커**
- 체력 높음, 이동 속도 느림
- 역할: "잘 안 죽는 적"이라는 긴장감

**유닛 B — 일반**
- 중간 체력, 중간 속도
- 역할: 기본 단위

**유닛 C — 빠른 유닛** (선택)
- 낮은 체력, 빠른 속도
- 역할: "놓치면 종점 빨리 닿음"의 긴장감

세 유닛 중 최소 **2종**이 구현되어야 한다. 3종은 권장.

### 2.4 방어 유닛 (2~3종)

**유닛 A — 근접**
- 짧은 사거리, 중간 공격력, 빠른 공격 속도

**유닛 B — 원거리**
- 긴 사거리, 낮은 공격력, 느린 공격 속도

**유닛 C — 특수** (선택)
- 예: 광역 공격 (스플래시) 또는 느리지만 높은 피해
- 2종으로 충분하면 생략 가능

세 유닛 중 최소 **2종**이 구현되어야 한다. 3종은 권장.

**공격 행동**: 사거리 내에 들어온 공격 유닛을 자동 타겟팅하여 공격한다. 타겟팅 규칙(가장 가까운 적 / 가장 앞선 적 / 가장 체력 낮은 적)은 에이전트 재량이되, 일단 하나로 고정한다.

### 2.5 배치

- 플레이어는 **배치 가능 타일**을 터치(모바일) 또는 클릭/드래그(에디터)하여 방어 유닛을 배치
- 배치되는 유닛의 종류는 **랜덤**. 플레이어는 선택하지 않는다.
- 타일당 1종만 배치 가능 (PRD A안 준수)
- 배치 후 제거/이동 불가

**배치 개수 제한**: 없음. 원하는 만큼 배치 가능.
**코스트**: 없음. Phase 0는 코스트 시스템 이전 단계.

> **노트**: "무제한 배치 + 랜덤 유닛"은 Phase 0가 재미없을 위험을 안고 있다. 하지만 이 단계에서 "재미있는 제약"을 넣기 시작하면 Phase 0의 범위가 부풀어 오른다. 제약의 부재가 오히려 "현재 루프가 얼마나 지루한지"를 드러내는 장치로 쓴다. 지루하면 Phase 1(드래프트 선택)과 Phase 4(코스트 제약)가 의미 있다는 신호다.

### 2.6 공격 타임라인 (공격덱) 스키마

Phase 0 공격덱은 다음 스키마로 정의된다. 구체 포맷(ScriptableObject / JSON)은 에이전트 재량:

```
AttackDeck {
  name: string
  spawns: [
    {
      trigger_time_sec: float     // 판 시작으로부터 초
      unit_type: UnitTypeId       // "tanker" | "basic" | "fast" 등
      path_id: PathId             // "A" | "B" | "C"
    },
    ...
  ]
  defeat_condition: {
    type: "enemy_reached_goal"
    count: int                    // 종점 도달 허용 수. 초과 시 패배
  }
}
```

Phase 0에서는 **2~3개의 고정 AttackDeck**을 미리 만들어둔다. 빌드 실행 시 에이전트가 지정한 방식(고정 / 랜덤 / 순환)으로 하나가 선택된다.

### 2.7 승패 조건

- **승리**: 타임라인의 모든 공격 유닛이 소멸됨
- **패배**: 경로 종점에 도달한 공격 유닛 수가 AttackDeck의 `defeat_condition.count` 초과
- **타이머**: Phase 0에서는 3분 타이머를 **두지 않는다**. 타임라인이 끝날 때까지 판이 진행된다. (3분 타이머는 실시간 긴장감 검증에 중요하지만, Phase 0는 "재미 있음/없음"의 1차 판단이 목표이므로 타이머 없이 먼저 확인한다. 타이머 도입은 Phase 0 검증 직후 재검토.)

### 2.8 결과 화면

**최소 구성**:
- "VICTORY" 또는 "DEFEAT" 텍스트
- "다시 시작" 버튼 (같은 판을 다시 플레이)
- (선택) "다른 공격덱으로" 버튼

결과 화면은 꾸밀 필요 없다. 기능만 동작하면 된다.

### 2.9 로깅 (최소)

Phase 0에서도 로깅은 첫 빌드부터 존재해야 한다. PRD 섹션 2.11을 기준으로 하되, Phase 0 단계에 해당하는 필드만 채운다:

```json
{
  "session_id": "...",
  "phase": "phase0",
  "timestamp": "...",
  "attack_deck_id": "...",
  "placements": [ {"unit_type": "...", "tile": [x, y], "time": ...} ],
  "result": { "outcome": "victory|defeat", "duration_sec": ..., "enemies_reached_goal": ... }
}
```

JSON 파일로 로컬 저장. 경로와 포맷은 에이전트 재량이되, Phase 1에서도 확장 가능한 구조여야 한다.

## 3. 종료 조건 (Done Criteria)

Phase 0는 다음이 **모두** 이진 통과해야 Phase 1로 이동한다.

### 3.1 기능 이진 체크

- [ ] Unity 6 프로젝트가 Entities 6.x 패키지와 함께 빌드됨
- [ ] 에디터 플레이 모드에서 맵(20×10 그리드, 2~3개 경로)이 표시됨
- [ ] 타임라인에 따라 2~3종의 공격 유닛이 경로 시작점에 등장
- [ ] 공격 유닛이 각자 지정된 경로를 따라 종점까지 이동
- [ ] 배치 가능 타일을 터치/클릭하면 랜덤한 방어 유닛이 생성됨
- [ ] 방어 유닛이 사거리 내 공격 유닛을 자동 공격
- [ ] 공격 유닛의 체력이 0 이하가 되면 소멸
- [ ] 종점 도달 수가 임계값 초과 시 "DEFEAT" 결과 표시
- [ ] 모든 공격 유닛 소멸 시 "VICTORY" 결과 표시
- [ ] "다시 시작" 버튼으로 같은 판 재시작 가능
- [ ] 판 종료 시 JSON 로그 파일이 로컬에 기록됨
- [ ] Android 실기기 빌드가 동작 (터치 배치 동작)
- [ ] 최소 1개의 AttackDeck에 대해 승리와 패배 양쪽이 재현 가능

### 3.2 아키텍처 이진 체크

PRD 섹션 1.1.1의 ECS 경계 규칙을 준수했는가.

- [ ] 공격 유닛 이동·체력·소멸 로직이 ECS 시스템에 있다
- [ ] 방어 유닛의 타겟팅·공격·데미지 적용 로직이 ECS 시스템에 있다
- [ ] UI / 터치 입력 / 결과 화면은 MonoBehaviour에 있다
- [ ] `BattleBridge`(또는 동등한 단일 클래스)가 MonoBehaviour ↔ ECS 통신의 유일한 창구이다
- [ ] `BattleBridge` 외부의 MonoBehaviour 코드에 `EntityManager` / `World.DefaultGameObjectInjectionWorld` 직접 호출이 없다
- [ ] 공격 유닛·방어 유닛·공격덱의 수치가 ScriptableObject 또는 데이터 파일에 있으며 하드코딩되지 않았다
- [ ] SubScene이 사용되지 않았다
- [ ] 네트워크 코드가 전혀 없다

### 3.3 주관 평가 (게이트)

위 이진 체크를 모두 통과해도 Phase 1로 가기 전에 다음을 팀 내부에서 판단한다:

- **3~5명이 Phase 0 빌드를 플레이했다**
- 플레이어가 "유닛이 밀려오고 있다"는 실시간 감각을 받았다 (설문 또는 인터뷰)
- 플레이어가 **스스로 "더 좋게 막으려면 뭐가 필요한가"를 자발적으로 말했다** — 이 발언이 Phase 1 이후 도입할 시스템(드래프트/스킬/인접 효과)의 동기를 증명한다
- 플레이어가 패배했을 때 **"어디서 놓쳤는지"를 언어화할 수 있었다** (H3의 선제 검증)

주관 평가에서 "재미있지도 않고 개선 욕구도 안 생긴다"는 신호가 다수면, **Phase 1로 넘어가기 전에 Phase 0의 밸런스 튜닝 또는 범위 조정**을 먼저 해야 한다. 재미없는 루프 위에 드래프트·스킬·시너지를 쌓아도 결과는 "복잡한데 재미없는 루프"가 될 뿐이다.

## 4. 에이전트 자율 결정 영역

본 문서는 "무엇을"과 "완료 조건"만 정의하고, 다음은 **구현 에이전트가 자유롭게 결정**한다. 에이전트가 결정한 내용은 Phase 0 완료 시 별도 문서(`phase0-decisions.md` 권장)에 기록하여 Phase 1 작성에 참고한다.

- 프로젝트 폴더 구조, 어셈블리 분리 여부
- 씬 구성 (단일 씬 / 멀티 씬)
- ECS Component 세부 설계 (이름, 필드 구성, 분리 단위)
- ECS System 세부 설계 (System 개수, 의존 순서, SystemGroup 구성)
- `BattleBridge`의 구체 클래스명과 책임 분할 (단일 클래스로 충분한지, 보조 클래스 필요한지)
- Baker 사용 여부 (ScriptableObject → Entity 변환 방식)
- 타겟팅 규칙 (가장 가까운 적 / 가장 앞선 적 / 기타)
- 경로 표현 방식 (waypoint 배열 / 스플라인 / 기타)
- 그리드 좌표계 구현 (int2 / Vector2Int / 커스텀)
- 유닛 비주얼 (Primitive / 단순 스프라이트 / 기타 — 기능 구분만 되면 됨)
- UI 프레임워크 (UGUI / UI Toolkit — 단, 일관성 유지)
- 테스트 전략 (EditMode 단위 테스트 / PlayMode 통합 테스트의 비율)
- 로그 파일 경로, 파일명, 회전 정책

**결정 원칙**: 애매하면 단순한 쪽. Phase 0는 검증용이지 최적 아키텍처 설계용이 아니다. 단, PRD 섹션 1.1.1 / 6.1 / 6.2의 경계·원칙·금지 패턴은 반드시 준수.

## 5. Phase 0 종료 시 에이전트에게 요청하는 산출물

- 동작하는 Unity 6 프로젝트 (에디터 + Android 빌드 가능 상태)
- 최소 1개의 EditMode 테스트와 1개의 PlayMode 테스트 (구체 범위는 에이전트 재량)

## 6. Phase 0 이후 Phase 순서 (참고용)

본 문서는 Phase 0만 상세화하지만, 작성 당시 합의된 전체 Phase 순서는 다음과 같다. Phase 1 이후 각 Phase의 상세 문서는 **직전 Phase 완료 후** 작성한다.

1. **Phase 0 — 실시간 디펜스 루프** (본 문서)
2. **Phase 1 — 드래프트** (10→7픽 도입, 랜덤 배치 제거)
3. **Phase 2 — 스킬** (스킬 2종, 코스트 시스템 도입 여부 이 시점에 결정)
4. **Phase 3 — 배치 시 효과 / 인접 시너지** (유닛 특성의 깊이 부여)
5. **Phase 4 — 그 외 마무리** (3분 타이머, 더미 봇 스코어, 결과 화면 비교, 측정 프로토콜)

이 순서는 **"가장 근본적인 재미"부터 "가장 파생적인 시스템"까지**의 순서이며, 각 Phase는 직전 Phase의 검증을 전제로 한다. 앞 Phase가 실패하면 뒷 Phase는 무의미하다.
