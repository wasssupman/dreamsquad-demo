# wide-board-camera — 판이 화면보다 큰 게 정상인 카메라

> ## 목표 3줄
>
> 1. **판 전체를 화면에 우겨넣는 프레이밍을 은퇴시킨다** — 카메라는 «판 전체»가 아니라 **«플레이어가 정한 관심점»**을 잡는다.
> 2. **팬을 개통한다.** 줌은 여전히 상태가 소유하고 플레이어에게 주지 않는다(핀치 없음).
> 3. **판 전체를 보는 것은 「동사」가 된다** — 오버뷰 버튼을 누르고 있는 동안만.

상태: **작성됨 2026-08-25** · 착수 전

## 이 spec 이 답하는 질문

> **판이 화면보다 커도 조작과 판독이 성립하는가?**
> 손가락 하나가 팬·배치·인스펙트·조준을 헷갈리지 않고 갈라내는가, 그리고 화면 밖에서 벌어지는 일을
> 플레이어가 «내가 안 봤다»로 납득하는가?

**이 spec 은 큰 맵을 만들지 않는다.** 기존 라이브 맵(Duel 23×10)에서 완결되고, 그 상태로 출하 가능해야
한다. 큰 맵 저작·밸런스는 후행 spec `wide-board-content`, 편성 확대는 `squad-slots-ten` 이다.
이 분리가 load-bearing 이다 — 세 덩어리를 한 spec 에 두면 카메라 커밋이 세이브 마이그레이션과
맵 밸런스에 인질로 잡힌다.

## 왜 지금 — 시스템이 판 크기에 막혀 있다

`map-rework` 계약 9 가 *"크기 유지(15×11/15×12) — **카메라·UI 를 건드리지 않는다.** 공간은 데코
축소로 번다"* 로 개편 5맵에 상한을 걸었고, **공성 맵 가족(Duel·Ford·Isle)의 상한은 별도로 테스트에
굳어 있다** — `Tests/EditModeAssets/MapDocumentPoolDevEntriesTests.cs` 의 `Width <= 23` / `Height <= 12`
(*"⑥ 카메라 불변 상한 — 더 넓히면 폰에서 판이 작아진다"*). 라이브 맵 Duel 은 이미 23×10 으로
**그 테스트 상한선**에 서 있다.

**이 spec 이 그 매듭을 푸는 쪽이다.** 맵을 넓히려면 카메라가 먼저 판보다 작아질 수 있어야 한다.

**순서 근거.** 0~1 은 **화면이 오늘과 똑같다**(관심점을 도입하되 값이 보드 중심 그대로) — 되돌리기가
싸다. 3 은 2 와 **같이 가야 한다**(진폭·흐림 기준이 같은 전환에 걸려 있다). 4 가 조작을 열고,
5 가 «전체를 보는 동사»를 준다. 6~7 은 4~5 이후 독립.

**중간 상태 고지 — 그림이 실제로 뒤집히는 것은 unit 4 커밋이다.** unit 2 는 가시 칸수 **기계**를
넣되 저작값은 폴백이 걸리는 값으로 둬서 화면이 안 바뀌고, **실제 칸수 인하는 팬이 열리는 unit 4 와
같은 커밋**에서 한다. 이렇게 나누지 않으면 unit 2~3 두 커밋 동안 화면 밖 셀에 배치할 수단이 없어
`DragPlacementReachTest`(도달성 계약)가 **빨간 채로 방치**된다. 그래서 모든 커밋이 플레이 가능하고
출하 가능하다.

## Feature-wide 계약 (load-bearing)

1. **관심점(focus)의 소유자는 `CameraDirector` 다.** 입력 컨트롤러는 **화면 델타만** 밀어 넣고
   (`SetPanDelta`, 기존 `SetDragFocus`/`Kick` 과 같은 방향), «델타 → 월드 이동 → 클램프 → 관심점»은
   Director 안에서 끝난다. 이유는 Director 의 명문 계약이다 — *"Director 가 맵이나 브리지에서
   bounds 를 당겨오지 않는 것이 계약이다 — 그 유혹이 경계 우회의 입구다. 입력은 브리지가 미는 한
   방향뿐이다"*(`CameraDirector.SetBoardBounds` 주석). 컨트롤러가 클램프하려면 bounds 를 별도
   경로로 또 가져와야 해서 이 계약이 깨진다.
2. **줌은 상태가 소유한다. 플레이어에게 주지 않는다.** 핀치(두 손가락 거리 = 줌)를 도입하지 않는다.
   **동시 터치는 「오버뷰 홀드(버튼) + 판 탭(워프)」 조합 하나만 허용**하고 그 외 제스처는 전부 단일
   포인터다 — 보드 위에서 두 손가락이 동시에 의미를 갖는 경우는 만들지 않는다(터치 규칙은 unit 5).
   줌 자유도는 사거리 원·데미지 넘버·VFX 진폭·오버헤드 UI·DoF 를 전부 줌 종속으로 만든다 — 그 축을
   열지 않는 것이 이 설계의 지불이자 이득이다.
3. **가시 영역은 「거리」가 아니라 「칸수」로 저작한다.** `fixedDistance`(월드 거리)로 저작하면
   화면비가 넓은 기기가 판을 더 본다 — 랭킹을 제출하는 비동기 토너먼트에서 **실력의 일부가 기기가
   된다.** 이 프로젝트는 절대 거리 저작이 화면비마다 무너진 사고를 이미 한 번 겪었고 그 기록이
   `CameraFramingMath.DofRange` 주석에 실측으로 남아 있다. 거리는 저작값이 아니라 **가시 칸수에서
   매 프레임 파생**된다(unit 2).
4. **`fitToBoard` 는 은퇴하지 않는다 — 오버뷰로 이사한다.** 오버뷰 레시피가 그 코드를 그대로 쓰므로
   `FitDistance` 는 삭제 대상이 아니다. 그리고 **작은 맵은 자동으로 오늘의 그림으로 폴백**한다
   (`min(저작 칸수, 보드 칸수)`) — 맵별 예외 코드를 만들지 않는다.
5. **오버뷰는 「누르고 있는 동안」이고, 잠그는 것은 커밋뿐이다.** 토글이 아니다 — 코스트 회복이 느려
   (`regenPerSec 0.35`) 2초 왕복의 자원 손실이 사실상 0 이라 「배치를 포기한다」가 대가로 성립하지
   않고 스팸을 부른다. 홀드는 손가락이 묶여 있어 읽기 전용이 자동 성립하고 체류가 자기 제한적이다
   (어휘 선례: 드림캐쳐 카드 슬로모, 수명 = press~release).
   그리고 잠기는 것은 **커밋**이지 arm·조준이 아니다 — 「armed 인데 멀리 놓고 싶다」가 새 제스처
   없이 이 한 글자로 풀린다: arm → 오버뷰 홀드 → 판 탭 = 워프 + arm 유지 → 평소처럼 배치.
   **엣지 오토팬은 만들지 않는다**(아래 「명시 제외」).
6. **팬은 기존 보드 제스처 소유자가 갖는다.** 새 포인터 소비자를 만들지 않는다 —
   `placement-armed-board-drag` README 「보드 press 소유권」(*"두 소비자가 같은 press 를 노리는 race
   재생산 금지"*, 원 계약은 `unit-dreamcatcher-inspect` 계약 11)을 그대로 재현하게 된다. 탭/드래그 임계는 **하나로 통일**한다(현재 보드 16px vs 인스펙트 24px 로
   갈려 있어 그 사이 밴드에서 둘이 동시에 산다).
7. **연출 채널의 진폭은 거리에 종속된다** — 카메라가 가까워지면 같은 월드 진폭이 화면에서 커진다
   (`CameraComposeMath` — `pos = basePos + baseRot * delta.localPos`). 그래서 unit 2 와 unit 3 은
   **같이 간다**. 근거·영향 채널 목록은 unit 3.
8. **화면 밖 상태를 알리는 신호는 통합 스트레스 비네트 하나다.** 미니맵·가장자리 적 지시자를
   만들지 않는다. 화면 가장자리는 이미 스트레스 비네트가 소유하고 있어(위험할수록 어두워지고
   심박으로 뛴다) 거기 지시자를 놓으면 **가장 필요한 순간에 가장 안 보인다**. 상세는 unit 7.
9. **모든 수치는 SO 에서** (제약 6): 가시 칸수·팬 감도·관성·오버뷰 전환 시간 전부
    `CameraDirectionConfig`. **관성 0 = 관성 끔** — 전역 토글을 다시 만들지 않는다
    (camera-direction unit 16 이 은퇴시킨 축).
10. **아키텍처 중립 계산은 순수 함수로** (제약 10): 클램프·가시 사각형·칸수→거리 역산은 plain
    in/out static + EditMode 테스트. **관성 적분은 새로 만들지 않는다** — 기존 스프링 스텝을
    재사용한다(제약 8).

## 명시 제외 (하지 않기로 결정)

- **핀치 줌 / 멀티터치** — 계약 2.
- **미니맵** — 사용자 결정 2026-08-24. 「상시로 위치를 보여주면 팬할 이유가 없어진다」.
- **화면 가장자리 적 지시자** — 계약 8. **자리가 없다**(화면 가장자리는 스트레스 비네트가 소유하고,
  하단은 트레이·독·손패가 100% 점유한다) — 이것만으로 기각이 성립하며 다른 spec 에 의존하지 않는다.
  보강 논거로, 마음이 체력을 공유하게 되면(`heart-stress-axis` unit 12) 「어느 마음이 맞는지」가
  전술적으로 무의미해져 표면 자체가 불필요해진다.
- **화면 밖 진입 루트 예고** — `spawn-point-alert` 의 스폰→골 경로 라인 트레일은 **화면 안 정보**다.
  판이 커지면 그 선의 상당 부분이 화면 밖에서 흐르는데, **이 spec 은 그걸 풀지 않는다.** 방향 화살표는
  경로를 나르지 못한다(그 spec 이 셰브론 반복을 이미 한 번 폐기했다). 후보는 후속의 「리드인 오버뷰
  초대」이고, 초대는 «지금 볼 때다»이지 «어느 길로 온다»의 대체가 아니다.
- **엣지 오토팬(드래그가 화면 가장자리에 닿으면 판이 밀린다)** — 검토 후 **폐기**. 하단 가장자리는
  100% UI 이고 트레이 rect 가 곧 취소존이라 「아래로 내린다」가 «취소»와 «남쪽으로 민다»를 동시에
  뜻한다. 더 나쁜 것은, 판이 손가락 밑으로 계속 미끄러져 **「밖에 놓으면 취소」가 물리적으로 도달
  불가**가 된다(`drag-cancel-affordance` 가 해결한 문제의 부활). 어포던스도 0 이라 가르칠 수 없다.
  대체는 계약 5.
- **큰 맵 저작 · 웨이브/코스트 밸런스** — `wide-board-content`.
- **편성 7→10 · 트레이 재구성** — `squad-slots-ten`.

**N/A** — 이 spec 은 플레이 오브젝트를 신설하지 않고 생성→렌더 경로도 바꾸지 않는다. 카메라 포즈의

## 검증 방향

- 클램프·가시 사각형·칸수→거리 역산 **EditMode 단위 테스트**.
- 기존 카메라 테스트 중 **에셋 레시피를 로드해 팬 최대에서 보드 코너를 재는 것**
  (`Tests/EditMode/CameraStatePoseTests.cs` 의 `AuthoredPlacementLead_KeepsBoardOnScreen_AtFullPan`)은
  **삭제가 아니라 계약 교체** — 대체 단언은 「클램프가 관심점을 보드 안으로 가둔다」다. 상세는 unit 2.
  (같은 파일의 `SolveStatePose_FitToBoard_…` 는 **자기 framing 을 합성**하므로 이 spec 으로 안 깨진다.)
  ⚠ 두 테스트 모두 순수 math 를 직접 부른다 — **Director 배선의 회귀 가드가 아니다.** 배선 검증은
  Play 스모크가 담당한다.
- **`DragPlacementReachTest`(도달성 계약)의 재정의** — 「상단 배치 가능 행에 바로 닿는다」가
  「**팬을 끝까지 민 상태에서** 닿는다」로 바뀐다. 개정 시점은 **unit 4**(칸수 인하와 같은 커밋).
- 실기 확인 3종(아래 「먼저 재야 할 것」)은 착수 전 스파이크.

## 먼저 재야 할 것 (착수 전 스파이크)

1. **`fovMin 31` vs 전투 레시피 `fov 25`** — 최종 FOV 가 클램프에 걸려 25 로 물러난 뒤 31 로
   렌더되고 있다(의도치 않은 여백). 의도인지 사고인지 정하기 전에는 어떤 거리 계산도 못 한다.
2. **남쪽 클램프 극단에서 판의 모든 행에 손가락이 닿는가** — 트레이(화면 y 32~190)와 판정 포인터
   오프셋(손가락보다 108px 위)이 겹쳐 하단에 약 298px 의 「손가락을 둘 수 없는 띠」가 있다.
   실측 결과는 **unit 1 이 저작할 `hudInsetBottom` 값과 남쪽 클램프 여유**를 정한다 — unit 0 의
   시그니처(뷰포트 비율 입력)는 실측과 무관하게 고정이므로 **unit 0 은 스파이크 전에 착수해도 된다.**
3. **배치 직후 arm 이 풀려 다음 드래그가 팬이 되는 문제** — 3분 판의 실제 리듬이
   「배치 → 즉시 다음 자리 스카우트」라 판마다 수십 번 난다. 샘 비율이 높으면 **연속 배치(커밋 후
   arm 유지)를 이 spec 안으로 끌어와야 한다** — 후속 후보로 미룰 수 없다.
   **결정 기록 위치**: 실측 결과와 판단을 이 항목에 한 줄로 확정 기재하고(예 *"2026-0X-XX 실측 —
   판당 N회, 승격함/안 함"*), 승격하면 `8_continuous_place.md` 를 새 번호로 만든다(handoff 는 9 로
   밀린다). 승격하지 않으면 아래 「후속 후보」의 해당 줄에서 「승격될 수 있다」를 지우고 이유를 남긴다.

## 후속 후보 (이번 범위 밖)

- **연속 배치(커밋 후 arm 유지)** — 스파이크 3 의 결과에 따라 이 spec 으로 승격될 수 있다.
- **오버뷰 판독 보강** — 큰 맵 오버뷰에서는 «어디가 급한가»는 읽히지만 «무엇을 내야 하나»(적 종류)는
  안 읽힌다. 먼저 오버뷰 전용 유닛 스케일 부스트(같은 그림을 크게)로 시도하고, 그래도 부족할 때만
  추상 글리프를 검토한다 — 「기존 어휘를 키우지 새 기호를 얹지 않는다」.
- **웨이브 리드인 구간의 오버뷰 초대** — 예고 2~2.5초는 아무 일도 안 일어나는 구간이라 오버뷰
  버튼이 짧게 스스로 어필할 자리다(각성 항아리 독 선례: 상시 어필 철거, 회차 오를 때만 0.3초).
  카메라를 뺏는 자동 peek 은 `camera-direction` 의 「카메라 탈취」 계약과 싸우므로 **초대까지만**.
- **「놓침 N」 판독** — 못 본 대가가 화면에 숫자로 없다. 은퇴한 스트레스 배지 슬롯이 비어 있다.
  → `wide-board-content` 「결정 노드」로 이관됨.
- **매치 진입 시 오버뷰 → 관심점 1회 비행** — 배치 페이즈가 꺼져 있어(3초 카운트다운) 판을 훑을
  시간이 0초다. 기존 상태 전환 비행을 재사용하면 싸고, 판의 범위를 가르치면서 오버뷰 버튼의 의미도
  심는다. unit 5 체감 확인 후 판단.
- **`BoardSortOrder` 행 밴드 결함** — 밴드가 `* 10` 이라 폭 23 에서 이미 `cellX >= 10` 이 행 밴드를
  침범한다(뒷줄이 앞줄을 덮는다). 지금은 두 셀이 화면상 멀어 안 보일 뿐이고 **큰 맵에서 실제로
  겹친다.** 한 줄 수정이며 회귀 테스트도 있다 — `wide-board-content` unit 0 소관.
