# unit 0 — 관심점 클램프 (순수 함수)

## 목적

카메라가 판 일부만 볼 때, **관심점이 나갈 수 있는 사각형**을 계산한다. 배선은 하지 않는다 —
이 unit 은 함수와 테스트만 만들고 화면은 오늘과 완전히 같다.

경계를 잘못 잡으면 판 가장자리가 영영 못 만지는 칸이 된다. 특히 **남쪽**이 위험하다: 하단 트레이
(화면 y 32~190)와 배치 판정 포인터 오프셋(손가락보다 108px 위 — `DragSwaySettings` 의
`placementPointerOffsetHeightRatio 0.1`)이 겹쳐 **하단 약 298px 이 「손가락을 둘 수 없는 띠」** 다.
클램프를 화면 사각형으로 잡으면 그 띠에 걸린 행은 팬을 끝까지 밀어도 배치가 안 된다.

## 변경 대상

- `Assets/_Project/Scripts/Presentation/CameraPanMath.cs` (신설)
- `Assets/_Project/Tests/EditMode/CameraPanMathTests.cs` (신설)

## 구현

네 함수 전부 plain in/out static (제약 10). `UnityEngine` 의 `Vector3`/`Quaternion`/`Bounds` 만 쓰고
씬·에셋·시간을 참조하지 않는다.

**1. 가시 지면 사각형** — 카메라 pose 에서 지면 평면(y = 보드 평면)이 화면에 덮이는 영역.
pitch 때문에 실제 모양은 **사다리꼴**이다(멀리가 넓다). 클램프에는 **보수적 내접 사각형**을 쓴다 —
가로는 사다리꼴의 **좁은 쪽(화면 하단)** 폭, 세로는 근평면~원평면 깊이.
사다리꼴 그대로 쓰면 판 모서리에서 보드 밖 여백이 화면에 들어온다.

**2. HUD 인셋** — 1의 결과에서 상·하단을 잘라 **실제로 손가락을 둘 수 있는 영역**을 낸다.
입력은 뷰포트 비율(0~1)이고, 하단 인셋 = `트레이 상단 + 판정 포인터 오프셋`을 호출부가 계산해
넘긴다. **함수는 트레이가 뭔지 모른다** — 비율만 받는다.

**3. 클램프** — 보드 bounds 를 2의 반폭만큼 안쪽으로 수축한 사각형에 관심점을 가둔다.
**보드가 그 축에서 화면보다 작으면 수축 결과가 뒤집히는데, 그때는 그 축을 보드 중앙에 고정**한다
(음수 폭을 0 으로 접지 말 것 — 접으면 작은 맵에서 관심점이 한쪽 모서리에 붙는다).

**4. 칸수 → 거리 역산** — unit 2 가 쓸 입력. 「가로 N 칸이 보이는 거리」를 pitch·수직 FOV·화면비에서
푼다. 구현은 **`CameraPanMath` 에 두고** 내부에서 `CameraFramingMath.FitDistance` 를 호출한다
(N×M 부분 사각형의 로컬 코너를 만들어 먹이는 얇은 어댑터). **`CameraFramingMath` 에 새 산식을
추가하지 않는다** — 두 파일에 같은 계산이 생기는 것을 막는 것이 이 문장의 목적이다.

## 완료 기준

- EditMode 통과. 최소 단언 5개:
  - 클램프 결과가 **항상** 보드 bounds 안이다(무작위 입력 fuzz 포함).
  - 보드가 화면보다 작은 축은 **보드 중앙에 고정**된다(폭 0 이 아니라 중앙).
  - 하단 HUD 인셋을 키우면 **남쪽 한계가 판 안쪽으로 밀린다**(그래야 하단 행이 손에 닿는다).
  - 같은 입력에 화면비만 바꿔도 **가시 칸수가 유지**된다(unit 2 의 전제).
  - 사다리꼴이 아니라 **내접 사각형**을 쓴다: 관심점을 한계까지 밀어도 보드 밖 좌표가
    가시 사각형에 들어오지 않는다.
- **화면은 아무것도 바뀌지 않는다.** 이 unit 은 호출처가 없다 — 코어 lane 전건 초록이 완료 조건.
