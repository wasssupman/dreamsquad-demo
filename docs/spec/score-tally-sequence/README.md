# score-tally-sequence — 결과 연출 페이즈 (점수 합산)

> 상태: **완료 2026-07-21** (units 0~2). 인계는 `3_handoff_summary.md`.

## 상위 목표

전투 종료 → **결과 연출** → 결과 화면. 지금은 종료 즉시 결과 화면이 뜬다.

연출 페이즈에서 우상단 HUD 점수에 **시간점수 → 스트레스점수**가 순차로 더해지고,
합산이 끝나면 결과 화면으로 넘어간다. 플레이어가 자기 점수가 **어디서 왔는지** 보게 하는 게 목적이다.

## 전제 정정 — HUD 점수는 킬점수가 아니었다

| | 현재 값 |
|---|---|
| HUD 점수 | 처치 1기당 **+10** (`ScoreHudView.pointsPerKill`) |
| 킬점수 | 잡몹 **100** / 보스 **2,000** (`AttackUnitData.killScore`) |

74기 전멸 시 HUD 는 740, 킬점수는 11,200 — **15배 차이**다. 이대로 연출을 붙이면
`740 → +11,500 → +7,200` 이 되어 첫 항만 축척이 다르고 최종 점수와도 안 맞는다.

**따라서 HUD 를 킬점수로 통일한다** (2026-07-21 결정). `battle-score-formula` README 의
후속 후보 *"라이브 HUD 점수 ↔ 최종 점수 통합"* 을 여기서 소화한다.

## 흐름

```
전투 종료 판정
  → [Tally 페이즈]
       0.0~1.0  전장 여운 + 딤이 서서히 (전투 HUD 는 이때 걷힌다 — 결정 D)
       ~1.0     배지 펄스 (시선 유도)
       1.54     "시간  +11,500"      ← 라벨 먼저
       1.78     HUD += 시간점수      ← 0.24초 뒤 숫자
       2.77     "스트레스  +7,200"
       3.04     HUD += 스트레스점수
       4.01     총점 확정
  → 결과 화면
```

시작 숫자는 전투에서 쌓인 **킬점수**다(unit 0 에서 HUD 를 킬점수로 통일했다).

패배도 같은 연출을 탄다. 다만 시간·스트레스가 0이라 **더할 게 없으므로 빠르게 지나간다** —
"0점을 굴리는" 민망한 장면을 만들지 않는다.

## 기존 자산을 그대로 쓴다

`ScoreHudView` 에 이미 있는 것:

- `_shownScore` → `_targetScore` **롤링 보간** (`rollLerp`) — 숫자가 굴러가는 연출이 이미 동작한다
- 마일스톤 플래시 · 글로우 · 펀치 스케일 (`score-hud-impact-upgrade`)

즉 **`_targetScore` 를 밀어주면 카운트업이 저절로 재생된다.** 새 롤링 로직을 만들지 않는다.

## feature-wide 계약

1. **점수 계산은 건드리지 않는다.** `ScoreMath` 는 이미 확정된 값을 주고, 이 spec 은 그걸 **보여주는 순서**만 만든다.
2. 연출 중에도 총점은 `score.Total` 과 정확히 일치해야 한다. 화면 합과 실제 제출값이 어긋나면 안 된다.
3. **서버 제출(`ReportMatchResult`)은 연출 시작 시점에 한다.** 연출이 끝날 때까지 기다리면 그동안 앱이 죽었을 때 기록이 사라진다. 화면 연출과 기록은 독립이다.
4. 롤링·플래시는 `ScoreHudView` 기존 연출을 재사용한다. 새 카운터를 만들지 않는다.
5. 연출은 **건너뛸 수 있어야 한다** (탭). 재시작 반복 시 매번 다 보는 건 고통이다.
6. ~~`TimeManager` 로 전투 시간을 멈춘다~~ → **불필요했다.** 전투 종료 시 `_running=false` 가
   `PushBattleRunningToEcs` 로 ECS `BattleRunning` 에 흘러 시뮬이 이미 멈춘다. 연출은 전부
   unscaled 로 돈다. `Time.timeScale` 금지는 그대로 유효(기존 제약).
7. 연출 중 결과가 두 번 확정되지 않는다 — 기존 `_resultShown` 가드를 유지한다.

## 결정 기록

**A. 축 순서 — `킬(이미 있음) → 시간 → 스트레스`.** 플레이 순서("빨리 끝냈다 → 안 흘렸다")를 따랐다.
시간이 보통 가장 크게 움직여 클라이맥스가 중간에 오지만, 순서의 자연스러움을 택했다.

**B. 길이 — 총 4.0초** (당초 제안 2~2.5초에서 늘림). 첫 구현이 2~3초대였는데
**"마지막 적이 끝나자마자 진행돼 인지가 어렵다"** 는 실사용 피드백으로 인지 단계를 쪼갰다.
늘어난 시간이 전부 인지에 쓰이고 전 구간 스킵 가능하다. 상세는 `2_tally_sequence.md`.

**C. 라벨 표기 — `시간  +11,500`.** HUD 배지 아래에 붙었다 사라진다. 결과 화면에 3축 분해가
이미 있으므로 여기서는 지금 더해지는 것만 보여준다. **폰트는 HUD 와 동일한 Kanit** 이어야
"같은 숫자가 자란다"로 읽힌다.

**D. Tally 진입 즉시 전투 HUD 가 사라지는 것 — 그대로 둔다** (2026-07-21 체감 확인).
`SetPhase(Tally)` 가 여운보다 앞이라, 손패·코스트·다음웨이브가 여운 1초 동안 걷힌 상태로
보인다. 코드 리뷰가 "문서와 실제가 다르다"고 지적했으나 실제로 보니 괜찮아서 **문서를
실제에 맞췄다** — 여운의 정의는 "전투 화면 그대로"가 아니라 **"HUD 가 걷히고 전장만 남은
마지막 킬의 여운"** 이다.
