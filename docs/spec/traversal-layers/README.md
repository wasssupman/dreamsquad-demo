# traversal-layers — 적 이동 가능 영역의 층 비트필드 (배치 층의 대칭)

상태: **작성 2026-08-07 · 사용자 승인 대기**

## 상위 목표

배치를 `placeMask × 유닛 층` 교집합으로 바꿨듯(placement-mask unit 4), **적 이동도 같은 모양으로** 만든다: 셀이 여는 **통행 층**과 적이 통행할 수 있는 **층 비트**의 교집합이 이동 가능성을 정한다.

```
통행 가능  ⇔  (셀 통행 층 & 적 통행 층) != 0
```

지금은 통행 가능 = `tiles == Walk` 하나로 고정이라, "이 적만 배치지면을 밟고 지나간다" 같은 걸 데이터로 만들 수 없다. 배치와 마찬가지로 **구현은 적 종류/클래스에 종속되지 않는다** — 코드는 비트만 보고, 어느 적에게 어떤 층을 줄지는 SO 저작이다.

## 왜 배치보다 무거운가 (핵심 설계 지점)

배치는 셀 판정 하나로 끝나지만 이동은 **경로**라서, 통행 집합이 다르면 **길찾기 결과가 다르다**. 현재는 전 적이 공유하는 flow field 1개이고, 런타임 벽 판정도 그 필드의 `flow==0` 에서 파생된다(`MovementCellTrim.IsWallCell`). 따라서 층을 도입하면 **통행 마스크별로 flow field 를 따로 만들어야** 한다.

채택: **매치에 실제 등장하는 통행 마스크 값마다 필드 1개**(로스터에서 결정론적으로 수집). 값 1종이면 지금과 완전히 동일한 1개다. 조합 폭발이 없고(마스크 값은 저작으로만 생김), 결정론은 "같은 로스터 = 같은 필드 집합"으로 유지된다.

## Feature-wide 계약

1. **층 정의는 배치와 공유**하되 축은 다르다 — `PlacementLayer` 는 "설 수 있는 칸", 통행은 `TraversalLayer`(별도 enum, 같은 [Flags] byte 문법). 한 필드로 겸직시키지 않는다: 도로는 "적이 지나가지만 지면 유닛은 못 서는" 칸이고 배치지면은 그 반대라, 두 축이 우연히 반대일 뿐 같은 값이 아니다.
2. **파생 기본값 = 현행 재현**: `Walk → Ground`(지상 통행), `Place/Deco/Env → 없음`. 적 SO 미지정(`None`) = `Ground` 폴백. 즉 **아무것도 저작하지 않으면 지금 판과 완전히 동일**하다(옵트인).
3. **결정론**: 필드 집합의 순서·내용은 로스터에서 결정론적으로 정해진다(마스크 값 오름차순). 같은 시드·같은 덱 = 같은 필드 = 같은 경로.
4. **벽 판정의 단일 정의 유지**: `MovementCellTrim.IsWallCell` 이 유일한 벽 술어라는 성질을 깨지 않는다 — 인자로 "그 적의 필드"를 받는 형태로만 확장한다.
5. **B-1 승계**: 유닛과 적은 여전히 서로를 막지 않는다. 이 spec 은 "어디를 지날 수 있나"만 데이터화하며 충돌/블로킹을 도입하지 않는다.
6. **스폰·골 칸은 항상 통행 가능**해야 한다 — 적이 나올 수도 들어갈 수도 없는 맵이 만들어지면 안 된다(빌드 시 강제 + 페인터 검증).
7. **성능 상한**: 필드는 마스크 값 종류만큼만. 종류가 3 을 넘으면 경고(콘텐츠 설계 실수 신호).
