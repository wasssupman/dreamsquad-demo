# traversal-layers — 통행 층 (유닛이 어디를 지날 수 있나)

> ## 목표 3줄
>
> 1. **sim 이 «이 칸이 어떤 종류인가»를 안다** — 지금은 «Walk 냐» 1비트만 안다.
> 2. **유닛이 «나는 어느 층을 지날 수 있나»를 갖는다** — 그리고 경로 계산이 그 교집합만 본다.
> 3. **그 첫 소비자는 «방어유닛이 자기 배치 영역 안에서만 움직인다»** 이고, 이 spec 은 **그 기계까지만** 만든다.
>
> 이 spec 은 **행동 변화 0 으로 끝난다.** 실제로 유닛을 움직이는 것도, 물타일을 만드는 것도 여기가 아니다.

상태: **rev 3 · units 0~4 완료 2026-08-09 · 행동 변화 0** ([4_handoff_summary.md](4_handoff_summary.md))
(rev 0 적 전용 초안 / rev 1 전 주체로 확장 / rev 2 «미래 융합 기반»으로 재정의 / **rev 3 = rev 2 계약이 라이브를 깨뜨려 재작성**)

## 0. 왜 재작성했나 — rev 2 계약이 라이브를 깨뜨렸다

**rev 2 계약 1(«셀 층 비트필드 한 벌을 배치·통행이 공유한다»)이 틀렸다.** 그대로 구현한 unit 1b(`fd25d53b`)가 **적이 한 발도 안 움직이는** 상태를 만들었다.

1. `BattleBridge` 는 필드를 굽기 직전(`:1061-1070` `CloseCellLayers`) **스폰·골 칸의 `placeMask` 를 0 으로 닫는다** — «적이 튀어나오는 칸 위에 방어유닛을 못 세운다»는 배치 불변식이다.
2. 1b 는 `cellLayers = Sanitize(placeMask)` 였다 → **골의 통행 층 = 0**
3. `FlowFieldBuilder:100` 이 `walkMask[srcIdx] == 0` 인 소스를 버린다 → **유효 소스 0**
4. `dist` 전 셀 `MaxValue` · `flow` 전 셀 zero → `MovementSystem` 이 `FlowRecovery` 까지 zero 를 받고 `continue`

### 근본 원인 — 두 축은 다르다

`placeMask` 의 저작 의미는 **«어느 유닛이 여기 설 수 있나»** 이지 «어떤 종류의 칸인가»가 아니다. 실측(`MapDocument_Test`): `Walk` 칸 **23개에 마스크 0** — *"여기 **배치** 금지"* 이지 *"여기 **통행** 금지"* 가 아니다. 통행으로 읽으면 통로 23칸이 라우팅에서 사라지고 데코 7칸이 새 통로가 됐다.

과설계 리뷰가 *"두 축이 달라야 할 칸의 예가 지금 하나도 없다"* 고 했는데 **있었다.** 스폰·골 칸이 매 판 그 예다.

**수정 완료**(`43b714d1`): 통행 층은 `PlacementLayers.Derive(tiles[i])` 로만 만든다. 그러면 `cellLayers` 는 `walkMask`(1비트)의 **N비트 일반화**가 되어 라우팅과 벽 충돌의 정의가 **갈릴 수 없다**.

### 이 실패에서 나온 규칙 (§7 계약 6·7 로 승격)

| 무엇을 놓쳤나 | 규칙 |
|---|---|
| `placeMask` 의 **writer**(`CloseCellLayers`)를 안 봤다. 읽는 쪽만 조사했다 | 데이터를 재사용하겠다고 쓰기 전에 **그 배열의 writer 를 전수**한다 |
| 주석 한 줄(*"층 이름은 공간 기준"*)을 데이터 계약으로 승격했다 | 계약의 근거는 주석이 아니라 **실제 에셋 값**이다. 한 번 열어본다 |
| «기존 테스트 기대값 갱신 0건»을 «행동 변화 0» 의 증거로 썼다 | 관련 테스트가 전부 `GeneratedMap` 을 직접 만들어 **라이브 경로를 우회**한다. 그 주장은 **라이브 경로를 타는 테스트**가 있을 때만 |

## 1. 무엇을 만들고 무엇을 안 만드나

판정식은 하나다.

```
통행 가능  ⇔  (셀 층 & 유닛 통행 층) != 0
```

**만든다**: 셀 축(sim 이 칸 종류를 안다 — 완료) · 유닛 축(유닛이 자기 층을 갖는다) · 소비 축(순찰 필드가 그 층으로 영역을 만든다).

**안 만든다**:

| 안 하는 것 | 왜 |
|---|---|
| **물타일** | 사용자 결정(2026-08-09). 타일 타입·아트·시각 어포던스 전부 범위 밖 |
| **골 필드 슬롯 다중화의 확장** | §2 — 이 spec 스코프에 **소비자가 0** |
| **로스터 수집** | 방어유닛 로스터는 필드 설치 시점에 **존재하지 않는다**(§2-3). 그리고 소비자도 없다 |
| **방어유닛 이동을 실제로 켜기** | §5 — 별도 spec. 여기는 기계까지만 |
| **통행 층 저작(페인터 브러시)** | 파생만 쓴다(§0). 저작이 필요한 실제 예가 생기면 그때 |

## 2. 범위를 정한 사실 — 골 슬롯의 소비자는 «적» 뿐이다

rev 2 는 «마스크별 골 필드»를 핵심으로 뒀다. **실측하니 이 spec 스코프에서 그 기계를 읽는 곳이 없다.**

**2-1. 순찰 필드는 골 슬롯을 안 쓴다.** `PatrolFieldSystem` 은 엔티티마다 `scratchFlow`/`scratchDist`(Temp)를 **즉석에서 굽는다**(`:52-53`). 골 싱글턴에서 가져가는 건 **마스크 하나**(`FillWalkMask`, `:50`)뿐이다. 방어유닛은 골로 가지 않는다.

**2-2. 골 슬롯을 읽는 곳은 전부 «골로 가는 적»이다.** `MovementSystem`(전진) · `AgentSeparationSystem`(전진 밀림 거부) · `BattleBridge`(스폰 분산·예고 라인) · `AttackSystem`(frontmost 순서·넉백 축) · `HealthThresholdSystem`(블링크 착지).

**2-3. 로스터 수집은 방어유닛에 대해 불가능하다.** `PrepareDraftMap()`(맵·필드 설치) → `SetDefenderPool()` 순서다(`GameManager.cs:329 → :349`; 드래프트 경로도 `:304 → DraftController:124`). **필드를 굽는 시점에 이 판의 방어유닛이 누구인지 아무도 모른다.** 소환물은 더 늦다(전투 중 생성).

### 결론 — 1a·1b 는 동결한다

행동 변화 0 이고 «적 통행 층이 갈리는 날»의 seam 으로 정확히 맞다. 그러나 **더 키우지 않는다** — 슬롯 수는 1로 두고 로스터 수집은 만들지 않는다. 물 적 spec 이 올 때 그쪽이 자기 맥락에서 수집 시점을 푼다.

**셋 다 «행동 변화 0» 으로 끝난다.** 이 spec 의 산출물은 «기계가 서 있고, 아무도 아직 켜지 않았다» 이다.

### ⚠ unit 2 의 폴백이 이 spec 에서 가장 위험한 지점이다

rev 2 계약 2 는 «미지정 시 방어유닛 = 자기 `placementLayers`» 였는데 **그대로 두면 unit 3 이 판을 바꾼다.**

순찰 소환물은 `placementLayers` 가 이니셜라이저 잔여값 `Ground` 인데 **실제로는 Walk 층에서 돈다** — 앵커가 `TryGetNearestWalkCell` 로 Walk 셀에 스냅되기 때문이다. `Ground` 로 폴백하면 앵커가 자기 마스크 밖 → 영역 마스크 전부 0 → **순찰병이 굳는다.**

**따라서 폴백은 «전원 `Path`»(= 현행 `walkMask` 재현)로 못박는다.** «방어유닛 = `placementLayers`» 는 방어유닛 이동을 켜는 별도 spec 의 몫이다.

## 5. 이 spec 이 끝난 뒤에도 남는 것 (별도 spec)

「방어유닛이 배치 영역 안에서 움직인다」를 실제로 켜려면 아래가 필요하다. **여기서 하지 않는다.**

| 남는 것 | 근거 |
|---|---|
| **«Place = 벽» 하드 전제 3곳 뒤집기** | `BattleBridge.cs:2246` `TryGetNearestWalkCell`(`MapTileType.Walk` 하드코딩 — 앵커 스냅) · `PatrolAreaMath.cs:128`(주석이 *"방어유닛 자기 셀 = Place = 벽 전제"* 라고 못박음) · `FlowFieldBuilder.cs:191`(`CollectDefenderSources` 가 중심 셀 제외) |
| **좌표 권위 split-brain** | `DefenderTile` vs `LocalTransform` — 사직서·레드불·아군장판·해저드검증·시너지·효과타일·점유격자 **8곳** |
| **어그로 정적 전제** | `AggroChaseCell` 은 «목적지가 정적»을 전제로 1회만 굽는다. 가디언이 움직이면 적이 옛 자리로 걷는다 |
| **재배치 공존** | `DefenderRelocationController` 가 자기 `PatrolAnchor` 를 옮기는 경로가 없다 |
| **`SyncPatrolViews` 이중 동기화** | `PatrolAnchor` 보유 전 엔티티를 순회 — 방어유닛에 붙이면 재배치 비행이 깨진다 |

## 7. Feature-wide 계약

1. **통행 층은 `tiles` 에서만 파생한다.** 저작된 `placeMask` 를 읽지 않는다 — 두 축은 다르다(§0). `cellLayers` 는 `walkMask` 의 N비트 일반화이며 **두 정의가 갈릴 수 없다**는 것이 요점이다.
2. **미지정 폴백 = 전원 `Path`** (= 현행 재현). «방어유닛 = `placementLayers`» 는 이 spec 밖이다(§4).
3. **클래스 비종속.** 코드가 적/방어유닛/보스를 구분하지 않는다. 판정은 비트 교집합 하나다.
4. **벽 술어는 `NavGrid` 하나.** 마스크별로 **조립**될 뿐 술어가 두 벌이 되지 않는다.
5. **골 슬롯은 1개로 동결.** 소비자가 생기기 전에 늘리지 않는다(§2).
6. **데이터 재사용 전 writer 전수.** 다른 시스템의 배열을 읽겠다고 쓰기 전에 그 배열에 **쓰는** 코드를 전부 확인한다.
7. **«행동 변화 0» 은 라이브 경로 테스트가 있을 때만 주장한다.** 픽스처 그린은 증거가 아니다.
8. **B-1 승계.** 유닛과 적은 서로를 막지 않는다. 충돌/블로킹을 도입하지 않는다.

## 8. 미결 (착수 전 확정)

**D1 — 슬롯 매칭이 완전일치인가 교집합인가.** 현재 `SlotFor` 는 `maskValues[i] == unitLayers` **완전일치**이고 못 찾으면 조용히 primary 로 떨어진다. 유닛이 `Ground|Path`(=3)를 갖고 슬롯이 `{1,2}` 면 **경로 유닛이 지면 필드를 따라간다.**

**판정: 교집합이 맞다**(`(maskValues[i] & unitLayers) != 0`). 다만 슬롯이 1개인 동안은 무해하므로 **코드를 고치지 않고**, 테스트가 완전일치를 «정답»으로 고정하고 있다는 것만 주석으로 표시한다 — 물 적 spec 이 그 테스트를 근거로 완전일치를 계승하지 않게.

**D2 — 미등록 마스크를 조용히 폴백할까 경고할까.** 지금은 조용히 primary. 소환물처럼 로스터에 없던 유닛이 오답 슬롯을 써도 안 보인다. 슬롯이 1개인 동안 무해 — **슬롯을 늘리는 spec 이 결정한다.**
