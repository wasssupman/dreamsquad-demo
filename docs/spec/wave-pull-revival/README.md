# wave-pull-revival — 웨이브 당기기 복귀 (스케줄 편집기로서의 당김)

> ## 목표 3줄
>
> 1. **당기기를 플레이어에게 돌려준다** — 기능(`ForceNextWave`)은 살아 있고 버튼만 떼어져 있다. 되돌리되 무한 스태킹은 막는다.
> 2. ~~**당김이 도박이 아니라 판단이 되게 한다**~~ — 예고를 같은 릴리즈에 넣으려 했으나 **unit 7 에서 은퇴**(2026-08-21). 좌하단 폭 예산(≤300)에서 «상시로 읽히는 예고»와 «원뎁스 조작»이 양립하지 않아 조작을 골랐다.
> 3. **묶음 한가운데에도 고민을 만든다** — 지금은 3웨이브 내내 같은 성격이라 묶음 안에서는 당길지 말지가 무차별하다. 가운데 한 번을 섞는다.

> **unit 1(다음 웨이브 예고)은 unit 7 에서 은퇴했다** — 계약 4 · PRD §6.3 미채택. 근거는 [7](7_one_depth_pull.md).

## 상위 목표

`three-minute-survival` unit 2 가 당기기를 껐다. 당시 판단은 **점수가 처치로만 벌리면 당김은 곧 «더 받기»여서 항상 옳은 선택이 된다**는 것이었다. PRD 는 그 전제를 뒤집는다 — 공급이 3분 안에 다 소화될 수 없게 넘치므로 당김은 «더 받기»가 아니라 **«무엇과 무엇을 겹칠 것인가»** 가 된다. 그러면 항상 옳은 선택이 아니게 되고, 덱마다 답이 달라진다.

코드로 보면 복귀 비용은 낮다. `BattleBridge.ForceNextWave()`(`BattleBridge.cs:2137`)는 이벤트 구동 경로가 완비돼 있다 — 즉시 큐잉 · 타임아웃 타이머 재기준 · 리드인 유지 · `wave_forced` 로그. PlayMode 스모크 3개가 이걸 판 진행 동력으로 계속 써 왔기 때문에 썩지 않았다. 실제로 없어진 것은 **도크 버튼 · 튜토리얼 안내 · 클리어 어필** 세 개뿐이다.

그래서 이 spec 의 무게중심은 «되살리기»가 아니라 **«당김이 판단이 되는 조건 세 개»** 에 있다: 상한 · 예고 · 묶음 내 변주.

## Feature-wide 계약

1. **당김은 스케줄 편집기지 가속 버튼이 아니다.** 탭 1회 = 다음 웨이브 1개 즉시 투입. 홀드·연속 가속 없음. **전투 타이머는 당기지 않는다** — 몰아 불러 빨리 끝내는 보상은 없다(PRD §2.1, `wave-pattern` unit 9 비목표 승계).

0. **상한 knob 은 «적 웨이브 덱»의 것이지 플레이어 로드아웃의 것이 아니다.** `maxPullsPerClear` 는 `AttackDeck`(맵과 짝지어 시드가 고르는 적 편성)에 있고 **전 참가자가 같은 값을 받는다**. PRD §5 의 「덱 아키타입」은 플레이어 로드아웃을 가리키는 **다른 것**이다 — 이 knob 을 로드아웃으로 옮기면 「내 덱이 남보다 많이 당긴다」가 되어 PRD §2.3(동일 시드·동일 스트림)이 깨진다. 문서에서 「덱」이 어느 쪽인지 헷갈리면 이 항목을 본다.

2. **상한은 «정리한 뒤로 몇 번 얹었나»다.** 필드를 비우면(전멸 진행) 0 으로 돌아가고, 당길 때마다 1 오른다. 상한에 닿으면 더 못 얹는다. N 은 덱 필드로 저작한다(제약 6).
   **«기본 스케줄 대비 선행 N웨이브»(PRD §4.2 문구)를 그대로 쓰지 않는 이유**: 빨리 밀면 자동 진행도 함께 빨라져 «선행» 상태가 되는데, 그 계산식은 **잘 막은 플레이어의 당김을 막는다.** PRD §2.1 은 정반대를 요구한다 — 「빠른 안정화 → 다음 공세를 더 일찍 투입할 선택권 획득」. 정리로 리셋되는 카운터가 그 문장을 그대로 구현하고, 막으려던 것(겹쳐 쌓기)도 정확히 같은 값으로 잡힌다.

3. **당김이 막힐 때 버튼은 사라지지 않고 잠긴다.** 사라지면 «왜 없지»가 되고, 아무 반응이 없으면 «고장났나»가 된다. 잠금 상태와 «언제 풀리는지»를 같은 자리에 표시한다.

4. ~~**예고는 실제 스폰과 같은 데이터에서 나온다.**~~ **은퇴 2026-08-21 (unit 7)** — 예고 자체가 사라져 소비처가 없다. 다만 «선언한 편성 = 실제 스폰» 불변식은 생성기의 것이라 `WaveGroupsMatchSpawnTests` 로 계속 산다. 예고를 되살릴 땐 이 항목부터 다시 켠다. 이하는 그때를 위한 원문:
    `GeneratedWave.groups`(유닛 × 수량)를 브리지 읽기 전용 창구로 노출하고, 도크와 드래프트 브리핑 스트립이 **같은 출처**를 읽는다. 스트립은 이미 `{유닛명} ×{수량}` 을 그리므로(`WavePatternStripView.cs:480`) 표현을 맞춘다. 예고와 실스폰이 갈리면 당김 판단 전체가 거짓말이 된다(`spawn-point-alert` 계약 승계).

5. **묶음 안에서 길(lane)은 계속 고정이다.** 변주는 **성격 슬롯만** 바꾼다. 길까지 흔들면 «여기를 보강하자»는 결정이 보상받지 못해 묶음 유지의 이점이 사라진다(`wave-concept-blocks` 계약 1 의 절반은 유지된다 — 개정 범위는 성격 축 하나).

6. **변주는 저작이 있을 때만 일어난다.** 컨셉 SO 에 변주 슬롯이 비어 있으면 현행대로 3연속 동일이다. 5종 중 일부만 저작해도 무회귀이고, 저작 안 된 컨셉이 조용히 깨지지 않는다.

7. **점수 가중치는 유지한다 (PRD §11 미채택 · 사용자 결정 2026-08-13).** PRD 는 전 적 동일 1킬을 요구하지만, ①방금 들어온 슬라임 분열이 `killScore` 0 으로 «원본 단위 1킬» 불변식을 이미 구현했고 평탄화하면 그 표현 수단이 사라져 슬라임 한 마리가 7킬이 된다 ②`three-minute-survival` 의 «가중 점수이므로 UI 라벨은 점수» 계약이 그대로 산다. **따라서 PRD §2.2·§10-5 도 함께 미채택**이며 랭킹 지표 라벨은 계속 「점수」다.

8. **결정론과 «같은 맵 = 같은 웨이브»는 불변이다.** 당김은 **소비 순서를 바꾸지 않는다** — 웨이브 내용은 이미 생성이 끝난 플랜에서 순서대로 나가고 당김은 «언제»만 바꾼다. unit 2 의 변주는 생성 시점에 결정되므로 `waveSeed` 파생이어야 하고, 컨셉 저작이 바뀌는 만큼 편성 baseline 은 깨진다(`waveGeneratorVersion` 3 → 4).

9. **기준선은 가짜이고, 가짜인 것이 화면에도 코드에도 드러나야 한다 (unit 3).** 규칙 셋:
   ① **이름이 약속을 하지 않는다** — 화면 문구는 「목표 페이스」다. 「진출 예상선」은 실제 10인 분포 컷을 약속하는 말이고, 전투 중 매초 들어오는 거짓 피드백은 판당 한 번인 랭킹 피드백보다 강해서 습관을 잘못 굳힌다.
   ② **출처는 함수 하나** — 서버가 생기면 그 안만 바꾸고 표시 코드는 안 건드린다(인터페이스를 만들지 않는다, 제약 8).
   ③ **제출값·로그·결과 화면에 절대 새지 않는다** — 새는 순간 «가짜 경쟁 기록»이 진짜 기록인 척 저장된다.
   축은 **처치 수가 아니라 점수**다(계약 7 로 가중치를 유지했으므로 PRD §7.1 예시의 「N체 부족」은 「N점 부족」이 된다).

10. **새 ECS 컴포넌트·시스템·맥락·이벤트 채널을 만들지 않는다.** 이 spec 은 브리지 스케줄러 · 생성기 · UI 세 곳에 갇힌다. 적 엔티티는 자기가 몇 번 웨이브에서 왔는지 모르고, **알 필요도 없다** — 계약 2 의 상한이 «웨이브별 생존 수»가 아니라 «필드가 비었나»(기존 `NoQueuedAttackersRemain`)로 판정하기 때문이다. 적에 웨이브 번호를 다는 순간 이 spec 은 ECS 변경 spec 이 된다.

## 파이프라인 커버리지

**N/A — 신규 플레이 오브젝트가 없다.** 당김은 기존 `QueueWave` 한 경로를 지나고(리드인·스폰 예고·펼침 전부 공유), 변주는 생성기가 고르는 유닛이 바뀌는 것뿐이라 스폰 이후 정거장이 동일하다. 새 ECS 컴포넌트·이벤트 큐·View 풀·씬 오브젝트가 없어 `docs/reference/object-pipeline-map.md` 갱신 대상이 아니다. 신규 SerializeField 는 도크 UI 값이며 `NextWaveDock` 이 자기 캔버스를 코드로 짓는 기존 방식을 따른다(씬 wiring 없음).

## 후속 후보

- **진출 예상선을 진짜 데이터로** [M] · unit 3 은 저작 곡선으로 **감각만** 만든다. 실제 10인 분포를 받으려면 경기 중 서버 조회가 필요한데 그 경로 자체가 없다(`TournamentApi` 는 시작·완료·랭킹 조회뿐). 백엔드 계약이 서면 unit 3 의 출처 함수 하나만 교체한다(계약 9).
- **경기 후 상위 플레이어 당김 시점 비교** [M] · PRD §7.2. 원재료(`wave_forced` 로그)는 unit 5 로 확보되지만, 남의 스냅샷을 받아오는 API 가 없다. 위 항목과 같은 백엔드 묶음.
- **워크벤치 봇 검증 V1~V6** [L] · PRD §9 는 이걸 구현 착수 **전** 선행으로 둔다. 시뮬레이션 하네스가 전무해 이 spec 안에서 만들 수 없다 — 별도 spec. **다만 V2(최대 당김 봇 소화율 < 100%)는 공급량 조건이라 당김 복귀와 직결**되므로, unit 0 에서 «상한까지 계속 당겨도 3분 안에 전량 소화되지 않는가»를 실측 1회로 대신한다.
- **공급량 재저작** [M] · PRD §3.1 은 「기본 진행만으로 3분 내 전량 소화 불가」를 요구한다. 현재는 100웨이브 명목에 실도달 10~16 이라 공급 자체는 남지만, 곡선이 «소화 못 할 만큼»으로 저작됐는지는 미검증. 위 실측 결과에 따라 판단.
- **엔드리스 규칙 재설계** [M] · `three-minute-survival` 후속 후보에서 이관. 엔드리스의 검증 질문(「당기기로 킬을 벌고 누수로 깎이는 리스크/리워드」)이 당김 복귀로 **되살아난다** — 그 spec 의 계약 4 를 다시 볼 수 있게 됐다.
- **클리어 어필 복원** [S] · `nextwave-clear-attention` 은 «누를 것이 없다»는 이유로 은퇴했다. 누를 것이 생겼으므로 근거가 사라졌지만, 자동 진행도 함께 사는 구조라 어필이 «눌러야 한다»는 오해를 만들 수 있다. unit 0·1 체감 후 판단.
- **원탭 재시작 확인** [S] · PRD §2.4(재도전 마찰 제거). 결과 화면 재시작 경로와 드림캐처 구성 복원이 실제로 원탭인지 미확인.
- **당김 대기 큐 상한 N 의 실측 튜닝** [S] · unit 0 은 어림값으로 시작한다. PRD §10-2 는 이 값을 봇 검증(V1~V3) 결과로 정하라고 하며, 그 전까지는 체감 기반 잠정값이다.
