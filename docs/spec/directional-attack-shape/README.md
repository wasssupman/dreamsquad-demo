# directional-attack-shape — 공격 판정에 「방향 항」을 더한다

> 상태: **초안 2026-09-11 · 기획자 리뷰 반영 2026-09-12** — 사용자 결정 9건 확정(아래). units 0~4 미착수.
> 선행: `distance-based-range`(완료) — 이 spec 은 그 spec 의 `11_facing_retirement.md` 가 예고한
> *「연속 좌표에서 성립하는 새 어휘(부채꼴·유닛 폭 직사각형)」* 다. 폐기된 것은 «폭 0 셀 레인»이지
> 방향성 자체가 아니었다.

## 배경 — 오늘 전투 판정에 방향이 0 이다

전투 판정 술어는 하나다(제약 13, `SkillMath.Reach` private · 진입점 `ReachFromUnit`/`ReachFromCell`):

```
도달 ⟺ |Δ|² ≤ (사거리 + 원점 항 + 대상 몸)²       ← 360° 원, edge-to-edge
```

근접/원거리·아군/적이 전부 이 하나를 지난다(`AttackReach.cs` 헤더의 소비처 12곳). 근접만 다른 것은
`attackTargetCount`(근접 전용 다중 타격 캡)와 대상 통행 층뿐이다. 그래서 **다중 타격 대상은 원 안에서
«가까운 순서대로 N체»** 이고 — 등 뒤의 적도 똑같이 맞는다.

| 근접 유닛 | 사거리 | 동시 타격 |
|---|---|---|
| 배스티온 · 브루저 · 말파이트 | 1 | 3 |
| 가디언 | 1 | 2 |
| 힐러(아군 힐) | 2 | 3 |

## 검증 질문

> **「타겟 방향으로 N°」를 저작한 유닛의 다중 타격이 그 부채꼴 안에서만 일어나고,
> 저작하지 않은 유닛(=360°)의 타격 집합은 오늘과 비트 단위로 같은가.**
>
> ⚠ 직사각형(Rect)은 이 질문의 **대상이 아니다**(결정 8). 코드 경로(술어·bake·게이트)는 이 spec 이
> 만들고 테스트하지만, 라이브 저작과 Play 검증은 긴창 유닛 spec 이 한다 — 사거리 1 유닛에 폭 1 상자는
> 곧 원이라 오늘 유닛으로는 실증이 성립하지 않는다.

## 사용자 확정 결정 (2026-09-11)

1. **도형은 «누구를 때릴 수 있나»(주 대상 획득)를 바꾸지 않는다.** 360° 원으로 탐색 → 최적 타겟
   선정 → **그 타겟 방향으로** 도형을 세워 판정식을 적용한다. 주 대상은 정의상 도형 안이므로
   「부가 타격만 자른다」와 「타격 집합 전체에 도형을 적용한다」는 **같은 결과**다. 은퇴한 facing 을
   되살리지 않는다.
2. **타격 수는 `attackTargetCount` 그대로.** 도형은 «후보 필터»이지 «타격 집합»이 아니다.
   긴창의 관통감은 N 을 크게 저작해서 낸다.
3. **적용 범위 = 모든 유닛 공격(아군+적).** 저작 기본값이 360° 라 오늘 동작은 전부 그대로다.
4. **판정은 자유각, 캐릭터는 좌우 반전만.** 방향은 타격 순간의 **지면 VFX** 가 보여준다(unit 3).
   몸통 각도와 판정 각도의 미세 불일치는 수용.
5. **스키마 = `AttackOutput` 형태**(kind enum + 이름 붙은 flat 필드, 형마다 파라미터 **하나**).
   탐색 결과는 `1_authoring_and_bake.md`. `[SerializeReference]`·별도 SO·사전 정의 도형 enum 은 기각.

**기획자 리뷰 반영 (2026-09-12)** — 리뷰 요지는 하단 「리뷰 기록」.

6. **참격의 정체는 «방향»이다.** 리뷰가 «뭉침»(주 대상 중심 스플래시)을 더 싸고 정직한 대안으로 제시했으나
   사용자 결정: 「휘두르는 쪽만 맞고 등 뒤는 안 맞는다」가 목적. 부채꼴 유지. 대가(한 복도 흐름에선
   360° 와 집합이 거의 같고, 근접 몸 항이 각도를 삼킨다)는 알고 간다 — unit 4 실효각 표.
7. **저작 금지 계약은 두지 않는다.** 도발 탱커(AggroCapacity)는 예외로 둘 필요 없음 — 저작자가 판단한다
   (unit 4 에 재료: Pass A 가 «새로 온 놈» 쪽을 보므로 붙잡은 팩이 부채꼴 밖으로 밀릴 수 있다).
   힐러는 그냥 360° 로 둔다(기본값 — 아무것도 안 하면 된다). 계약 9(경고)는 그대로.
8. **Rect 는 코드까지, 저작은 긴창 유닛 spec 으로.** 술어(unit 0)·bake(unit 1)·게이트(unit 2) 전부 구현·
   테스트하되 라이브 저작·Play 육안은 이관. 게이트까지 넣는 이유: bake 는 되는데 게이트가 무시하는 kind
   는 「저작했는데 조용히 안 되는」 함정이다.
9. **적에도 저작한다 — 보스 1종을 unit 4 후보에.** 「보스가 휘두르는 쪽만 맞는다」는 읽기(옆으로 돌아
   배치하면 덜 맞는다)를 만든다.

## 핵심 형태 — 게이트, 대체가 아니다

```
주 대상   = Reach(…)                        ← 오늘 그대로. 원. 무변.
부가 타격 = Reach(…)  AND  ShapeGate(Δ, u)   ← 새 항. u = 주 대상 방향
```

- **반경 항은 손대지 않는다.** 제약 13 의 산식은 문자 그대로 남고, 도형은 그 위에 곱해진다.
  도형을 반경 판정의 «대체»로 만들면 「도달」의 정의가 유닛마다 갈린다 — 그게 `distance-based-range`
  가 없앤 ①번 문제(누가 묻느냐에 따라 뜻이 달랐다)의 재현이다.
- **게이트는 좁히기만 한다.** 360° 에서 항등 → 저작 안 한 유닛은 오늘과 집합이 같다 → **골든 코퍼스
  무변**(unit 4 가 코퍼스 덱의 유닛을 저작하지 않는 한). 밸런스는 한 방향(덜 때림)으로만 움직인다.
- **도형은 「얼마나 멀리」를 정하지 않는다.** 반경도 길이도 `attackRange` 가 소유한다. 직사각형에
  길이를 따로 주면 `> 사거리` 는 무의미(획득 밖)이고 `< 사거리` 는 모순(주 대상을 못 때림)이다.
  그래서 형마다 필요한 수치가 **하나**다 — 원은 각도, 직사각형은 폭. 직사각형의 먼 모서리가 반경 원에
  **둥글게 깎이는 것은 의도**다(「창 길이 = 사거리」).

## feature-wide 계약

1. **진입점은 `SkillMath` 에만 신설한다.** `AttackReach` 는 타일 변환 래퍼(계약 8 — 본체는 엔진 무참조
   asmdef). 호출부가 도형 판정을 인라인으로 다시 쓰면 리뷰 거절.
2. **주 대상은 항상 통과한다** — `Δ` 와 `u` 가 같은 방향이면 두 도형 모두 true. 이 불변식이 테스트로
   고정된다(결정 1 의 «같은 결과» 가 여기 걸려 있다).
3. **몸 걸침 = 히트.** 대상 몸 원이 도형 가장자리에 걸치면 맞는다(「닿아 보이면 맞는다 · 그림자가
   진실이다」). 원점 항은 `Reach` 가 이미 갖고 있으므로 게이트는 **대상 몸만** 본다.
4. **sim 은 각도를 모른다.** 저작 각도 → bake 1회 `(sin, cos)` · 폭 → 반폭. 술어는 dot/cross 와 제곱
   비교만(`SkillCone.cosSq` 선례). sqrt·삼각함수 0.
5. **정의역 = 전체각 (0°, 180°] ∪ {360°}.** 그 사이(reflex)는 bake 가 **에러 로그 + 360 취급**.
   폴백이 360 인 이유: 게이트라 fail-open 이 안전하다(반대면 저작 실수 하나가 유닛을 무력화한다).
6. **0 = 미저작 = 360.** 기존 에셋 YAML 에 키가 없어 struct 가 0 으로 오고, 코드에서 만드는
   `AttackState`(도발 공격·v1 투사체)도 0 이다. 둘 다 오늘 동작이어야 한다. 이니셜라이저와 bake
   폴백 **이중**으로 막되 정본은 bake 쪽이다.
7. **방향이 정의되지 않으면(주 대상이 같은 자리) 게이트는 전부 통과.** `SkillCone.SameSpotEpsSq` 선례.
8. **사거리 링은 원 그대로.** 링은 「주 대상 획득 범위」를 말하고 그건 여전히 원이다 — 부채꼴로 그리면
   화면이 규칙을 **틀리게** 가르친다. 방향은 타격 순간의 VFX 몫.
9. **저작 유닛의 `attackTargetCount == 1` 이면 도형은 효과 0** → `OnValidate` 경고(저작 낭비 감지,
   `AttackUnitData` 의 「감지 저작했는데 outputs 비었다」 경고 선례).

## 범위 밖 / 후속 후보

- **긴창 전용 신규 유닛 + Rect 라이브 저작·Play 검증**(결정 8) — 이 spec 은 Rect 의 코드 경로까지.
  Spine 창 리그·찌르기 모션·저작·육안은 그 spec 이. 사거리 2 이상이어야 상자가 원과 갈린다.
- **스킬 광역에 방향 항** — `AreaSleepSkill` 등이 `attackTargetCount` 를 읽지만 원으로 모은다.
  같은 진입점을 쓸 수 있게 열어 두되 저작 안 함.
- **투사체 스플래시**(`ProjectileData.splashRadius`) — 착탄점 중심 = 「자리에 떨어지는 것」이라 형이 다르다.
- **`SkillCone.IsInCone` 흡수** — 드래곤 브레스. 몸 걸침이 없고 cos² 트릭이라 정의역이 90° 에서 잘린다.
  백로그 *「`SkillCone` 부채꼴 거리 게이트(양쪽 몸 0)」* 와 같은 항목.
- **끝을 보는 눈(frontmost) 카드 × 도형** — frontmost 는 락 제외 4종이라(`AttackSystem.cs:843` 계약 2)
  「매 공격마다 지금의 최전방」= 도형이 매 스윙 재조준된다. 카드는 유닛 저작으로 못 막는다 — 수용,
  계약으로만 명기(히스테리시스는 넣지 않는다 — 락이 그 역할이고 frontmost 는 락의 예외가 정체성).
- **가디언 × 끝을 보는 눈(frontmost) × 도형** — `SelectTargets` 뒤에 primary 를 frontmost 로 swap 하는데
  게이트 방향은 swap 전 primary 를 향한다. 삼중 조합이 희귀해 수용, 기록만.
- **reflex 부채꼴(180°~360°)** — 두 반평면의 여집합이라 같은 dot 두 번으로 되지만 플레이 가치가
  360° 와 구분되지 않아 층을 안 만든다(제약 8).

## 리뷰 기록 — 게임플레이/액션 기획자 관점 (2026-09-11, critic·Fable)

**판정**: 형태(게이트·자유각·링 원 유지·VFX 로 방향)는 옳다. 판정을 몸통에 묶으면 은퇴한 facing 의
재림이고, 링을 부채꼴로 그리면 화면이 규칙을 틀리게 가르친다.

**가장 무거운 지적**: *「이 형태가 만드는 것은 「방향」이 아니라 「뭉침」이다.»* 원점 고정 + 방향이 주 대상을
따라가므로 플레이어 규칙은 「때린 놈 근처만 같이 맞는다」. 한 복도로 흘러오는 판에서 360° 와 부채꼴은
대부분의 프레임에서 같은 집합이고 합류점·포위에서만 갈린다 → **사용자 결정 6**(방향 유지).

**허점 → 처분**:
| 허점 | 처분 |
|---|---|
| 근접 몸 항이 각도를 삼킨다(저작 90° ≈ 실효 130~150°) | unit 4 실효각 표 + 60° 이하 권장 |
| 도발 탱커: Pass A primary = «새로 온 놈» → 붙잡은 팩이 밖 | 금지 안 함(결정 7) · unit 4 재료로 |
| 힐러 부채꼴 힐 | 저작 안 함 = 360°(결정 7) |
| 「전방」 어휘 — 없는 facing 을 카드가 되살림 | unit 3 문안 「휘두르는 쪽」 |
| frontmost 카드 × 도형 = 매 공격 재조준 | 수용 · 후속 후보 기록(히스테리시스 안 넣음 — 락이 그 역할) |
| Rect 검증 유닛 부재 | 결정 8 |
| 락 해제 순간 방향이 튐 · 런너 락 시 부채꼴이 함께 회전 | 수용 — VFX 가 매번 찍혀 읽힌다 |

**기각된 대안**: 도형 유닛만 주 대상 규칙 변경(결정 1 파기·락과 충돌) · 4/8 방향 양자화(경계 flip-flop·
격자감 복귀) · 좌/우 반평면 기준(세로 진행에서 좌우가 가장 불안정) · 방향 히스테리시스(락이 이미) ·
인접 체인(스플래시 열화판) · 락 시점 방향 고정(주 대상 항등 파괴).
