# unit 6 — 아군 이동체 가독성 (식별 표식)

> **철회됨 2026-08-12 (사용자 결정).** 발밑 링을 제거하고 `AllyMarkerDecal.cs` 를 삭제했다.
>
> **이유: 이 unit 의 전제가 unit 8 에서 사라졌다.** 표식이 필요했던 근거는 아래 "목적"에 적힌 그대로 *"순찰병이 적과 같은 스켈레톤·같은 실루엣으로 걸어다닌다"* 였다. unit 8 이 고유 리그(Doll — 보라색 고양이 인형)를 입히면서 순찰병은 Casual Character 사람 실루엣의 적들과 **한눈에 구분된다**. 근거가 사라진 장치는 남기지 않는다.
>
> **부수 발견(같이 철회)**: 링이 소환물을 가리던 원인은 `SpineUnitView.UpdateSortingOrder` 가 `GetComponentsInChildren<Renderer>` 로 **모든 자식 렌더러를 캐릭터 대역으로 덮어쓰는** 것이었다(궤적 리그만 예외). 링이 저작한 -6 도, **블롭 그림자의 `ShadowOrder`(-5)도** 매 프레임 지워진다. 링을 없애면서 이 수정도 되돌렸다 — 리그 종류와 무관하게 **유닛 전원(44 = 파츠형 42 + 고유 2)** 의 그림자 정렬을 바꾸는 변경인데 링이 사라진 이상 동기가 없다. 그림자 대역이 실제로 덮이는 문제는 남아 있으므로 README 후속 후보로 이관한다.
>
> 아래 본문은 **당시 판단의 기록**으로 남긴다(선택지 A/B/C 와 겪은 함정 2개는 나중에 표식이 다시 필요해지면 출발점이 된다). 완료 기준은 무효다.

## 목적

이 게임에서 **화면을 가로질러 움직이는 것은 지금까지 전부 적이었다.** 순찰병은 그 전제를 깨는 첫 유닛인데, 적과 같은 스켈레톤(`Casual Character`)에 같은 실루엣으로 걸어다닌다. 플레이어가 적으로 오독하면 이 유닛의 배치 판단 자체가 성립하지 않는다.

unit 5 에서 함께 처리하려다 분리했다 — **어떤 표식을 쓸지가 육안 판정**이고(스펙이 처음부터 "Play 육안으로 고른다"로 유보), 판정 없이 하나를 구현하면 틀린 것을 만들고 다시 뜯을 위험이 있다. 항목을 unit 5 안에 미구현으로 남겨두면 "부분 완료"가 표에서 안 보이므로 별도 단위로 세운다.

## 현재 상태 (unit 5 종료 시점)

순찰병의 아군 신호는 **오버헤드 체력바의 defender 스타일 하나뿐**이다(`SyncPatrolViews` → `UnitOverheadUiLayer.SetUnit(entity, defender: true, ...)`). 이건 체력 표시의 부산물이지 식별 장치가 아니다 — 만피면 숨겨질 수 있고, 적에게도 체력바가 뜬다.

소환 순간의 `SpawnPlacementRing`(unit 5 ④)은 1회성 연출이라 상시 식별이 아니다.

## 선택지 (사용자 판정 필요)

**A. 발밑 아군 링/글로우** — 배치 하이라이트와 같은 색 계열의 상시 데칼.
- 기존 `BlobShadow.Attach(target, sprite, size, …)` 관용구를 그대로 쓸 수 있다(이미 유닛마다 붙는 발밑 데칼 계층이 있다).
- 이동형 아군이 늘면 **그대로 일반 규칙으로 승격**된다 — 후속 후보 "아군 이동체 가독성 일반 규칙"이 가리키는 방향.
- 약점: 소환사와의 관계를 말해주지 않는다. 순찰병이 여러 소환사에서 나오면 누구 것인지 모른다.

**B. 소환사 → 순찰병 연결선** — 두 유닛을 잇는 얇은 라인.
- "이건 내가 낸 것"과 "누가 냈나"를 동시에 답한다. 소환사가 죽으면 순찰병도 사라진다는 규칙이 화면에서 읽힌다.
- 약점: 이 유닛 전용이라 일반 규칙으로 승격되지 않는다. 라인 렌더러 계층이 새로 필요하다.

**C. 둘 다** — 링(아군임) + 연결선(누구 것인지). 비용이 가장 크다.

**결정: A (사용자 2026-08-03).** 일반 규칙으로 승격되는 쪽이고 기존 관용구를 재사용한다. 연결선은 "순찰병이 여러 기 나올 때"(다중 소환 후속 후보)가 실제로 오면 그때 B 를 얹는다.

## 구현

**새 에셋도 씬 배선도 만들지 않는다.** 링 스프라이트는 런타임 절차 생성 후 정적 캐시하고, 배치는 기존 발밑 데칼 계층 `BlobShadow.Attach(..., live: true)` 를 그대로 재사용한다 — 유닛 자식으로 붙어 매 프레임 따라가고 유닛 파괴 시 함께 사라진다(별도 회수 경로 불요).

**풀 재사용 오염 없음**: `SpineUnitView.Spawn` 이 `AddComponent<SkeletonAnimation>()` 을 하므로 뷰 GameObject 는 스폰마다 새로 만들어진다. 재활용된 뷰에 표식이 남아 적에게 붙는 사고가 구조적으로 불가능하다.

**부착 지점은 스폰(`CreatePatrolEntity`)이지 `SyncPatrolViews` 가 아니다.** 매 프레임 "이미 붙었나" 확인하는 상태를 만들지 않기 위함.

### 겪은 함정 2개 (값 바꿀 때 재발 주의)

1. **바깥 페더가 텍스처 경계에서 잘린다.** `OuterRadius + feather > 1.0` 이면 상하좌우 끝이 평평하게 깎여 링이 사각형처럼 보인다. 처음 값(0.98)이 정확히 그랬다 — 경계 알파가 0 이 아니라 115 로 남았다. 현재 `InnerRadius 0.64 / OuterRadius 0.90` 은 페더가 ~0.947 에서 끝나 안전하다.
2. **sortingOrder 충돌.** `ShadowOrder + 1` = −4 는 `TileGaugeOrder` 와 같은 값이다. 반대로 내려 `ShadowOrder - 1`(−6) 을 쓴다 — 링 띠는 `SizeMul` 덕에 그림자 원 **바깥**에 놓이므로 아래 깔려도 가려지지 않는다.

색·두께·크기는 `AllyMarkerDecal` 안의 프레젠테이션 상수다(`BoardSortOrder` 와 같은 급 — 유닛 스탯이 아니므로 SO 아님). 육안 튜닝 지점이 이 파일 하나라는 뜻이기도 하다.

검증은 절차 생성 텍스처의 **반경별 알파 프로파일**로 했다: 중앙 0 → r0.6 에서 44(안쪽 페더) → r0.7~0.8 에서 255(띠) → r0.9 에서 152(바깥 페더) → 경계 0.
