# squad-slots-ten — 편성 7종 → 10종 (초안)

상태: **초안 2026-08-25** · **착수 보류** — 세이브·게이트 축은 독립이라 언제든 병렬 가능
⚠ 슬롯 수가 10 이 아닌 값으로 확정되면 폴더를 `squad-slots-expansion` 으로 개명한다.
⚠ **전투 HUD 코너 예산은 A(`wide-board-camera`)와 공유한다** — A unit 5 의 오버뷰 버튼이 코너 위젯을
먹으면 슬롯 폭이 더 좁아진다. A 착수 후라면 그 결과를 읽고 슬롯 수를 확정한다.

> 이 문서는 스케치다. 착수 시점에 작업 단위를 확정하고 번호 파일을 쓴다.

## 목표

스쿼드 편성을 **7종에서 10종**으로 늘린다. `maxOnBoard 1`(고유 유닛)은 유지하므로 판 위 유닛도
7기 → 10기가 된다.

## 검증 질문

> 로드아웃 10칸이 아웃게임에서 성립하는가?
> 그리고 전투 트레이 10슬롯이 **실기에서 읽히고 눌리는가?**

## 왜 별도 spec 인가

「전장이 넓어졌으니 유닛도 늘린다」는 인과가 **산술적으로 성립하지 않는다**:

```
지금   23×10 = 230칸 / 7기  = 33칸당 1기
36×14 = 504칸 / 10기 = 50칸당 1기   → 밀도 0.65배
```

유닛을 43% 늘려도 면적이 119% 늘어 **밀도는 오히려 35% 떨어진다.** 밀도를 유지하려면 15기다.
즉 10종은 「넓어진 판을 채운다」가 아니라 **독립적인 편성 결정**이고, 지금 맵·카메라에서도 성립한다.

그리고 이 작업은 **세이브 마이그레이션과 출전 게이트**를 건드린다 — 카메라 spec 에 묶으면
카메라 커밋이 세이브 문제에 인질로 잡힌다.

## 함정 (착수 전 반드시 읽을 것)

**상수가 둘이다.** `SquadPreset.SlotCount`(칸 수)와 `SquadDraw.FieldCount`(출전 수)가 별개다.
`SlotCount` 만 올리면 페이지에 10칸이 뜨고 저장도 되는데 **판에는 여전히 7기만 나간다** —
컴파일도 테스트도 통과하는 **조용한 실패**다.

**둘 다 올리면 이번엔 게이트가 닫힌다.** `LoadoutGate` 가 `squadHave != squadNeed` 로 **정확히
같아야** 출전시킨다. `NormalizeSlots` 가 붙이는 건 **빈** 슬롯이라 기존 프로필은 7 ≠ 10 이 되고,
**전원이 3칸을 채우기 전까지 판에 못 들어간다.** 신규 프로필도 같다 — `defaultSquadUnits` 가
정확히 7개다.

**트레이 예산이 좁다 — 단 위기는 16:9 에서 먼저 터진다.** 트레이 폭은 슬롯 수에서 유도한 뒤 코너
예약폭으로 클램프된다. 캔버스가 **높이 기준 스케일**이라 폭은 화면비에 비례하고, 그래서 수치가 갈린다:

| | 16:9 (에디터 게임뷰 · 폭 1920) | 19.5:9 폰 (폭 2340) |
|---|---|---|
| 7슬롯 | **이미 클램프됨** (약 148px) | 클램프 안 걸림 (154px) |
| 8슬롯 | 약 131px | 클램프 안 걸림 (154px) |
| 10슬롯 | **약 106px** | 약 144px |

즉 *"7슬롯이 이미 클램프되고 있다"* 는 **16:9 에서만 참**이다. **unit 0 목업은 두 화면비를 같이
재야 한다** — 넓은 폰만 보면 문제가 없어 보인다(선례: 「화면비가 절대 거리 저작을 무너뜨린다」).

그리고 이 예산은 협상 불가다 — `battle-hud-legibility` 가 못박았다:
*"슬롯이 10개가 돼도 트레이는 안 넓어진다(클램프가 같고 슬롯만 좁아진다). 이 예산은 영구적이다."*
괄호 안이 이 spec 이 다루는 바로 그 메커니즘이다.

⚠ px→dp 환산(39dp / 48.5dp)은 기기 밀도 가정에 의존한다. **실기 1대에서 재고 그 기기를 적을 것.**

셀 안에 들어가야 하는 것: 포트레이트 · 이름 밴드 · 코스트 칩 · 쿨타임 림 · **소진 테두리 순환**.
마지막은 `defender-board-limit` 이 「셀 안에 새 기호를 넣지 않는다」는 결정 아래 만든 표현이라,
셀이 좁아질수록 내용 면적을 비례 이상으로 먹는다.

## 검토할 선택지

1. **8슬롯** — 16:9 에서 약 131px 로, 터치 타겟 관행을 지키는 마지막 정수. 7→8 도 판 위 유닛 +14%.
2. **셀을 줄이지 말고 셀 안을 줄인다** — 좁은 폭 구간에서 **이름 밴드를 끈다**(39dp 에서 어차피
   안 읽힌다). 정체성은 포트레이트가 이미 나른다.
3. **코너 예약폭 재협상** — 좌측은 여유가 거의 없다. 우측만 실측해 회수 가능한지 본다.
   회수 폭 40px 당 슬롯 약 **3.6px**(10슬롯) / **4.4px**(8슬롯), 화면비와 무관.
   **기대치를 낮춰야 한다** — 그리고 A 의 오버뷰 버튼이 이 예산을 먼저 먹을 수 있다.
4. **2단 트레이 — 권하지 않는다.** 높이가 두 배가 되면 하단 사각지대가 화면의 40% 를 넘고
   손패 fan 과 충돌한다.

## 결정 노드

- **기존 세이브를 어떻게 하나** — 빈 칸을 자동 충전할지, 게이트를 통과시킬지, 사용자가 채우게 할지.
  셋 다 product 결정이다.
- **토너먼트 덱 페이로드 길이** — 서버로 보내는 편성 문자열이 3종만큼 길어진다. 상한 확인 필요.

착수 시 `SquadPreset.SlotCount` 소비처를 **전수 grep** 한다 — 위에 적힌 것 외에 `PresetDiff`(저장 필요
여부 판정)·`PresetApply`·`ProfileStore`(신규 프로필 시드)가 최소한 더 있다.
