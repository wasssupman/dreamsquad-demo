# wave-concept-blocks — 웨이브 컨셉 블록 (3웨이브마다 편성의 성격이 바뀐다)

> ## 목표 3줄
>
> 1. **웨이브가 성격을 갖는다** — 「벌떼」·「중장」·「원거리」·「공습」. 랜덤 2종 편성을 의도된 조합으로 바꾼다.
> 2. **성격은 3웨이브 유지된다** — 웨이브당 12~18초라 매 웨이브 바뀌면 반응할 창이 없다. 블록 안에서 수량 곡선만 오르므로 «배우고 → 대응하고 → 겨우 버티고» 다음 컨셉이 온다.
> 3. **성질을 좁히면 스웜이 덩어리로 온다** — 뭉침을 런타임 속도 조작으로 만들지 않는다. 한 스웜의 성질 필터가 속도 폭을 좁혀 **저작으로** 모이게 한다.

상태: **설계 완료 2026-08-13 (rev 2) · 구현 미착수 · 다음 unit 0**

> **rev 2 (2026-08-13)**: rev 1 의 unit 0 「동행(스웜 속도 정렬)」을 **기각**했다. 스폰 시 `AttackUnitData.moveSpeed` 를 그룹 최저값으로 덮는 설계였는데, 이는 웨이브 생성이 아니라 **런타임 스탯 오버라이드**라 코어 로직을 침범하고 제약 6(모든 유닛 스탯은 SO 에서 나온다)과 마찰한다. 같은 효과를 저작으로 얻는다 — 아래 계약 3. 함께 `share`·`triggerOffsetSec`·`minLaneCount`·`cohesion` 4필드와 `PerGroupTimeline` 분기를 걷어냈다(과설계). 기각 사유는 「후속 후보」에 남겨 재조사를 막는다.

## 상위 목표

지금 웨이브는 11종 pool 에서 **균일 랜덤 2종**을 뽑아 전 lane 에 고르게 흩는다(`WavePatternGenerator.cs:120~153`). 그래서 웨이브 번호가 올라가도 바뀌는 것은 **수량뿐**이고, 플레이어의 결정은 매 웨이브 같다 — 이미 세운 방어선을 유지하는 것.

무필터 편성에는 부작용이 하나 더 있다. 한 웨이브의 적이 1.5~5.6 u/s 로 흩어져 도착해 하나씩 죽는다. 부딪히는 순간이 없고, 뭉쳐 있지 않으니 광역 스킬을 쓸 타이밍도 없다. **성질을 좁히는 것이 이 문제도 같이 푼다** — `Tanker` class 는 1종(1.5 단일), `Runner` class 는 2종(4.5·5.6)이라 성질로 좁힌 스웜은 속도 폭이 자동으로 좁다.

이 spec 은 컨셉을 **블록(3웨이브) 단위 편성 규칙**으로 도입하고, 라이브 덱에 아직 없는 비행 적(`Enemy_Skimmer`)을 「공습」 컨셉으로 편입한다.

## 검증 질문

> 3웨이브 블록 안에서 플레이어가 컨셉을 **읽고 대응을 완성**하는가 — 아니면 그냥 어려워진 것으로 느끼는가?
> 5개 컨셉이 **화면에서 서로 구분**되는가? 특히 「벌떼」와 「평소」가 다르게 보이는가?
> 「원거리」 블록에서 방어선이 깎이는 것이 재미인가 짜증인가?

## Feature-wide 계약

1. **컨셉은 블록의 속성이다.** 웨이브 i 의 컨셉 = 블록 `i / conceptHoldWaves` 에서 뽑힌 것. 블록 안에서 **컨셉과 lane 배정이 모두 고정**되고 수량만 곡선을 따라 오른다. lane 이 블록 안에서 바뀌면 «여기를 보강하자»는 결정이 보상받지 못해 블록 유지의 이점이 절반 사라진다.

2. **lane 은 절대 인덱스가 아니라 위상으로 말한다.** 슬롯은 `laneGroup`(같은 값 = 같은 lane, `-1` = 무지정) 만 갖고, 실제 lane 인덱스는 `waveSeed` 가 고른다. 그래서 한 컨셉 풀이 스폰 2~4개인 6맵에 그대로 쓰이고, 같은 「원거리」가 맵마다 다른 복도 쌍이 된다.

3. **이 spec 은 웨이브 생성 레이어에 갇힌다.** 신규 sim 시스템 0 · 신규 ECS 컴포넌트 0 · 신규 이벤트 채널 0 이고, **스폰 시 `AttackUnitData` 의 값을 다른 값으로 바꾸지 않는다.** 유닛 스탯의 유일 진실은 SO 다(제약 6). 따름정리 — **뭉침은 런타임이 아니라 저작으로 만든다**: 한 슬롯의 `classFilter` 가 속도 폭이 좁은 후보만 남기게 저작한다(`Tanker` 1종 = 1.5 단일, `Runner` 2종 = 4.5·5.6). 속도를 코드로 정렬하는 설계는 기각됐다(rev 2, 사유는 후속 후보).

4. **수량 총량은 곡선이 소유하고 컨셉은 `countMul` 로 스케일한다.** `ExponentialWaveTotal` 은 **개체 수**를 내므로 성질을 통일하면 난이도가 성질에 끌려간다(Runner 20hp × 19 = 380 vs Tanker 100hp × 19 = 1,900 — 5배). 배율 적용 후 하한은 `max(슬롯 수, round(total × countMul))`, 상한은 `maxUnitsPerWave`.

5. **필터는 fail-open 이다.** 슬롯의 `classFilter × altitude` 로 좁힌 후보가 0이면 필터를 버리고 전체 pool 에서 뽑고 **경고한다**. 빈 웨이브를 만드느니 컨셉을 포기한다(`ResolveWaveEligibleIndex` 의 판단 승계). 조용히 떨어지면 «컨셉을 저작했는데 편성이 안 바뀌는» 침묵이 된다.

6. **브리핑과 런타임은 같은 `laneCount` 를 넘긴다.** `Generate(deck, seed, laneCount)` 로 주입되므로, `BuildBriefingWavePlan` 이 다른 값을 쓰면 예고와 실스폰이 갈린다(`spawn-point-alert` 계약 위반). `laneCount` 는 `minLaneCount` 대신 슬롯의 distinct `laneGroup` 수와 비교되며 **결정론 키의 일부**다. 미확정(≤0)은 2로 폴백하고 경고한다.

7. **결정론은 유지되고 baseline 은 깨진다.** `waveSeed` 는 그대로이므로 «같은 맵 = 같은 웨이브»는 불변이다. 다만 웨이브당 rng 소비가 늘어(컨셉 1 + lane 1 + 슬롯당 1) **6맵 전부의 편성이 바뀐다** — 의도된 변경이며 `waveGeneratorVersion` 2 → 3 으로 표시한다.

8. **펼침은 `RoundRobin` 을 그대로 쓴다.** 슬롯이 라운드마다 1기씩 교차 emit 되고 시각은 `base + localIndex × spacing` 이므로 마지막 스폰이 `(total−1) × spacing` 으로 **현행과 동일**하다. 즉 **스폰 창 불변식과 `WaveKillBudgetPinTests` 는 손대지 않는다.** `PerGroupTimeline` 로 바꾸면 두 슬롯이 같은 순간에 겹쳐 스폰되어 케이던스만 나빠진다.

9. **컨셉이 방어유닛 사망을 새로 만드는 것이 아니다.** 적 전원이 이미 `targetFactions = 13`(`DefenderUnit|BlockingHazard|DefenderCore`)이고 `DefenderDeathEventsSingleton` 이 운영 중이다. 「원거리」가 하는 일은 **기존 압력의 밀도를 올리는 것**이다 — 그래서 컨셉 게이트를 늦게(웨이브 7+) 두고 실측으로 판정한다.

10. **공중은 «대응 불가»가 아니라 «스킬 한 발 값»이다.** 배치 유닛 중 `Path|Air` 는 `Defender_AntiAir` 하나뿐이지만(나머지 26종 `Path` 전용), **플레이어 스킬은 층 필터가 아예 없다**(`BattleBridge.cs:2431·2458·2501` — `_aliveAttackersQuery` 전원 + 타일 거리). 그래서 「공습」은 소수(`countMul` 0.3)·저HP·단일 종(속도 균일)이어야 하고, 무력감이 아니라 자원 지불로 번역되지 않으면 이 컨셉은 실패다.

## 후속 후보

- **⛔ 동행(스웜 속도 정렬) — 기각, 재조사 금지** · 스폰 시 한 스웜의 `moveSpeed` 를 그룹 최저값으로 덮어 진형을 유지하는 설계였다. 기각 사유: **웨이브 생성이 아니라 런타임 스탯 오버라이드**이고(Needler 2.8 이 Tanker 1.5 로 걸으면 이동·도달·어그로 체류·타겟 진입 순서가 전부 바뀐다), `AttackUnitData.moveSpeed` 를 유일 진실로 두는 제약 6 과 마찰한다. **같은 목적은 계약 3(성질 필터로 속도 폭을 좁히는 저작)으로 달성한다.** 다시 검토하려면 먼저 «저작으로 안 되는 컨셉»의 실제 사례를 하나 제시할 것.
- **보스 이동속도 저작 조정** [S] · **라이브 문제다.** 생성기는 보스를 선봉으로 스폰하지만(`WavePatternGenerator.cs:177`) `Boss_Nightmare` 는 **1.0 u/s 로 전 로스터 최저속**이고 호위 후보는 1.6~5.6 u/s 다. 경로 20셀·tileSize 1 이면 호위가 ~3.6~12.5초, 보스가 ~20초 — **호위가 통째로 죽고 10초 뒤에 보스가 혼자 걸어온다.** `Enemy_Boss_Nightmare.moveSpeed` 1.0 → 1.6 내외, `Boss_Mamemo` 1.4 도 함께 검토. SO 값 수정이라 코드 변경 0 이지만 보스 도달 시간이 줄어 난이도가 오르므로 별도 판단이 필요하다 — 그래서 이 spec 밖이다.
- **「전위·후위」(탱커 뒤 원거리)** [M] · 이 세트에서 가장 디펜스다운 컨셉(적에 층이 생기면 우선순위 결정이 생긴다). v1 에서 빼는 이유는 두 개다: ① 원거리 5종이 뭉쳐 오는 압력의 세기를 실측 없이 게이트로 정할 수 없다 ② **동행 기각으로 진형 유지 수단이 없다** — Tanker 1.5 가 최저속이라 뒤에 낸 Shooter(1.6~2.8)가 전부 추월한다. 성립시키려면 Shooter 속도를 Tanker 아래로 내리는 저작 조정이 선행이며, 그건 12종 전역 밸런스 변경이다.
- **위치 전용 컨셉(순수 「협공」·「일점 돌파」)** [S] · v1 은 성질 컨셉이 위상을 하나씩 갖고 태어나므로 위치 전용이 없어도 대비가 성립한다. 컨셉 수를 늘릴 때 추가.
- **슬롯 `share`(비중) 되살리기** [S] · rev 2 에서 삭제(저작 5종 전부 균등 또는 단일 슬롯이라 미사용). 「전위·후위」처럼 1:2 비중이 필요한 컨셉이 생기면 그때 필드를 연다.
- **컨셉별 `holdWaves` 오버라이드** [S] · v1 은 덱 단일값 3. 「공습」만 2웨이브처럼 컨셉마다 다르게 하고 싶어지면 그때 연다(제약 8).
- **곡선을 개체 수 → HP 예산으로** [L] · `countMul` 은 계약 4 문제의 실용 우회다. 근본은 곡선이 예산을 소유하고 성질이 그 예산을 개체로 환전하는 것. 밸런싱 전면 재설계라 별도 spec.
- **대공 가능 방어유닛 확대** [M] · 「공습」 반복 실패가 관측되면 원거리 몇 종에 `Path|Air` 를 연다. `waypoint-flight-enemy` 후속 후보(「대공사수 고유 아트·최종 수치 밸런싱」)와 같은 자리.
- **보스 치환을 컨셉 풀로 통합** [M] · unit 3 은 보스 웨이브를 «암묵 컨셉»으로 두고 호위만 블록 컨셉을 입힌다. 보스 자체를 `WaveConceptData` 한 항목으로 승격하면 저작이 한 축으로 모이지만, 지금 합치면 변경 두 개가 한 커밋에 겹친다.
- **카메라 가시성 확인** [S] · 위상 컨셉(협공)은 **두 입구가 화면에 동시에 보여야** 성립한다. 안 보이면 «화면 밖에서 뚫렸다»는 불공정감이 된다. 보드 전체가 담기는지 확인하고, 아니면 협공을 「인접한 두 lane」으로 제한한다.
