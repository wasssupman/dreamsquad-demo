# unit 14 — 값 이관 · 다맵 검증 · 문서 갱신

## 목적

세 상태의 실제 값을 채우고, 크기가 다른 맵에서 프레이밍이 성립하는지 확인하고,
바뀐 계약을 문서에 반영한다. 앞 유닛들이 구조를 세웠다면 이 유닛은 **눈으로 맞춘다.**

## 변경 대상

- `Assets/_Project/Data/Camera/CameraDirectionConfig.asset`
- `docs/spec/camera-direction/README.md`

## 구현

**시작값** (2026-08-21 결정. 배치의 거리·화각은 눈으로 튜닝할 몫):

**정본은 에셋이다** (`CameraDirectionConfig.asset`). 아래는 2026-08-21 튜닝 종료 시점의 값이고,
이후 인스펙터에서 바뀔 수 있다 — 이 표를 근거로 에셋을 되돌리지 말 것.

| | 배치 | 전투 |
|---|---|---|
| 대상 | 보드 중앙 → 커서 부분 추종 | 보드 중앙 |
| `pitchDeg` | 70 | **50** |
| 거리 | fit, `fitMargin` 1.15 | fit, `fitMargin` 1.0058 |
| `screenY` | 0.554 | 0.5543 |
| `fov` | 35.9834 | 35.9834 |
| 흐림 | **끔 (`dofEnabled` false)** | `1.0 ~ 1.6`, `dofMaxRadius` **1.0** |

`placementFocusLead = 0.15` (전역). 배치 `fitMargin 1.15` 가 주는 여유가 21×12·16:9 에서
약 0.14 NDC 라, 이보다 크면 손가락을 판 끝으로 끌 때 반대쪽 판이 화면 밖으로 나간다
(0.35 는 화면폭의 12% 만큼 나갔다). `AuthoredPlacementLead_KeepsBoardOnScreen_AtFullPan`
테스트가 **에셋 값을 읽어** 이 성질을 지킨다 — 리터럴을 박지 않는다.

전투 흐림 `1.0` 은 **판 뒷단**이다. 판 위의 것은 어느 줄이든 또렷하고 그 너머 원경만 빠진다.
캐릭터는 투명 큐라 깊이를 쓰지 않아(뒤에 있는 것의 깊이를 받는다) 판 안에서 흐림을 걸면
뒷줄 유닛의 머리 쪽이 배경 깊이로 흐려진다 — 그래서 시작점을 판 밖으로 밀었다.

전투는 `pitch 47 / fitMargin 1.0058 / screenY 0.5543 / fov 35.9834` 조합에서 출발했고,
그 값이 2026-08-21 사용자가 손으로 잡은 포즈 `(0, 15.85, -15.86)`(21×12·16:9)을 정확히
재현한다. 이후 사용자가 pitch 를 **50** 으로 튜닝했다.

**그 출발 조합은 산식의 회귀 기준으로 테스트에 남아 있다**
(`SolveStatePose_KnownGoodInputs_ReproduceReferencePose`). 그 테스트의 리터럴은 에셋 값이
아니라 «이 입력 → 이 출력» 이라는 산식의 기준점이다 — 저작값이 움직여도 빨개지지 않고,
`SolveStatePose` 를 잘못 건드리면 빨개진다. 둘을 헷갈려 테스트를 에셋에 맞추지 말 것.

**밸런스 수치를 리터럴로 못박지 않는다** — 테스트는 "보드가 화면에 들어온다", "대상이
`screenY` 에 온다" 같은 성질을 단언하고, 위 표의 숫자 자체를 기대값으로 굳히지 않는다.
단 전투 회귀 기준 하나는 예외로 남긴다(사용자가 눈으로 확정한 값이라 표류를 잡아야 한다).

**씬 카메라는 건드리지 않는다.** 런타임이 더 이상 읽지 않으므로 에디터 그림과 실제 플레이가
어긋날 수 있지만, **런타임이 안 읽는 값을 위해 dirty 씬을 저장하는 것**이 이 프로젝트에서
반복 사고가 난 축이다(미저장 WIP 가 통째로 베이크된다). `CameraDirector` 인스펙터에
"이 카메라의 씬 포즈는 런타임에 쓰이지 않는다" 를 명시하는 것으로 끝낸다.
