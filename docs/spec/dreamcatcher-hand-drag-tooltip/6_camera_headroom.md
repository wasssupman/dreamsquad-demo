# 6 — 폰트 확대 + 손패 연동 카메라 헤드룸

> 파일번호 5 는 의도적으로 비어 있다. 배너형 시도가 커밋 전에 철회됐다(아래 "철회된 시도").
> 코드 주석의 `unit 6` 과 번호를 맞추기 위해 6 을 쓴다.

## 목적

unit 4 로 툴팁을 압축했지만 두 문제가 남았다(사용자 실기기 확인 2026-07-21):

1. **본문 19pt 가 눈에 안 들어온다** — 모바일 가독성이 이 위젯의 존재 이유인데 미달
2. **여전히 보드를 가린다** — 압축만으로는 폭이 좁아 세로가 길어지는 구조를 못 벗어난다

폰트를 키우고(패널이 더 커진다), 그만큼의 상단 여백을 **손패가 열린 동안만** 카메라로
확보한다.

## 철회된 시도 — 배너형 (커밋 없음)

"빈 공간은 납작하고 넓은데(1520×151) 패널은 좁고 길다(480×221)" 는 진단으로, 폭을
세이프에어리어 좌측~점수 HUD 좌측 끝까지 늘리고 높이를 눕히는 안을 구현했다가 **철회**했다:

- **좌상단 `MenuButton` 과 충돌.** 씬에 직접 authoring 된 버튼(앵커 (0,1), pos (24,−24),
  170×64)이라 코드 기반 UI 조사에서 누락됐다. 배너가 x 40 부터 시작해 정통으로 겹쳤다.
- **폭이 넓어지니 줄당 글자가 늘어 폰트가 상대적으로 더 작게 느껴졌다** — 원 불만(가독성)을
  악화시켰다.

교훈: **화면 상단 점유 조사는 코드 생성 UI 만으로 불충분하다.** 씬 authoring 요소
(`m_Name:` grep)를 반드시 함께 본다.

## 구현

### A. 폰트 확대

- `tooltipHeaderFont` 22 → **27**, `tooltipBodyFont` 19 → **23** (둘 다 SerializeField 승격)
- 본문 안 축·타입 줄의 인라인 크기: `BodyCompact` 만 절대 `22` → 상대 **`115%`**.
  절대값이면 본문(23)보다 작아지는 **역전**이 일어난다. `Body()` 의 절대 22 는 그대로 두어
  덱빌더·덱 페이지·유닛 인스펙트 출력은 불변(unit 0 회귀 금지 계약).

### B. 카메라 헤드룸 채널 (`camera-direction` 확장)

**손패가 열린 동안만** 카메라를 눕히고(pitch) 물린다(dolly). 닫으면 스프링 복귀.

- `CameraDirectionConfig` 신설 노브
  | 필드 | 값 | 의미 |
  |---|---|---|
  | `handHeadroomPitchDeg` | **−2** | 홈 60° → 손패 열림 **58°**. 1도당 약 25px |
  | `handHeadroomDolly` | **−1.5** | 후퇴 = 줌아웃. 보드 약 8.5% 축소 |
  | `handHeadroomSpring` | 90 | 가중치 도달 속도 |
  | `handHeadroomDamping` | 14 | 2√90≈19 미만 → 살짝 오버슈트 |
- `CameraDirector.SetHandHeadroom()` — **피드 주도** 채널. `DreamcatcherHandView.Update` 가
  `State == Hand` 인 동안 매 프레임 호출하고, 2프레임 끊기면 자동 해제된다.
- `KeyringSim.SpringStep` 에 **float 오버로드** 추가(가중치 0↔1 추종). 첫 소비처가 이 채널.

## 되돌리면 안 되는 것

- **피드 주도 + 자동 해제가 핵심이다.** 명시적 `Release()` 구조로 바꾸면 닫힘/페이즈 이탈/
  강제 종료/씬 파괴 중 경로 하나만 빠뜨려도 카메라가 기운 채 남는다. 지금은 `State` 가
  `UnitStrip` 이 되는 순간 피드가 끊겨 복귀가 보장된다.
- **`headroomActive` 를 `anyActive` 에 포함해야 한다.** 빼면 Director 의 idle 최적화
  (`_settled`)가 한 프레임 만에 홈 포즈로 덮어써 헤드룸이 조용히 죽는다
  (`inspectActive` 가 같은 이유로 포함돼 있다 — 그 주석 참조).
- **`enableNonDragEffects` 로 게이팅하지 않는다.** 그 토글은 앰비언트 연출(킥/펄스/브리딩/
  비행) 억제용이고 현 에셋에서 꺼져 있다. 묶으면 기능이 조용히 죽는다(인스펙트 선례).
- **스프링 안착 판정은 가중치 절대값 + 속도를 함께 본다.** 언더댐핑이라 0 을 스쳐 지나므로
  `weight > 0` 만 보면 복귀 도중 idle 최적화에 얼어붙는다.
- **손패 연동이지 툴팁 연동이 아니다.** 카드 press 마다 카메라가 움직이면 멀미가 난다.
  또한 손패가 열린 동안은 화면 하단을 카드가 이미 덮고 있어, 보드를 아래로 밀 때
  **잃는 영역이 이미 가려진 곳**이다 — 비용이 필요한 순간에만 발생한다.

## 남은 가림 (의도된 트레이드오프)

−2°/−1.5 는 카메라 이동을 작게 유지하려는 사용자 선택이며, 그 대가로 침범이 남는다:

| | 값 |
|---|---|
| 보드 상단 | 156px → **233px** |
| 툴팁 하단 (폰트 확대 후) | ~316px |
| 남는 침범 | **약 83px** |

침범 구간은 보드 **상단 중앙부**(스폰 직후 경로)이고 스폰 지점 자체는 좌·우 끝단이라
가려지지 않는다. −6°/−2.5 면 침범이 0 이 되지만 카메라 이동이 눈에 띈다 — 그쪽이 더
거슬린다는 판단으로 현 값을 택했다(사용자 결정 2026-07-21).

수치는 씬 포즈 기반 **계산값**이다. 조정은 전부 인스펙터에서 Play 중 가능하다.
