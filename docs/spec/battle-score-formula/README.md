# battle-score-formula — 최종 결과 점수 산식 재설계

> 상태: **완료 2026-07-20** (units 0~5). 인계는 `6_handoff_summary.md`.
> 남은 것: 유출 한계 10 의 플레이 감각 확인(사용자 판단).

## 상위 목표

현재 최종 점수는 `BattleBridge.CalculatePlayerScore()` (`:3741`) 의 단일 식이다.

```csharp
return Math.Max(0, (int)(durationSec * 10f - _goalReachedCount * 50));
```

입력이 경과시간과 유출 수 둘뿐이고, **오래 끌수록 점수가 오른다** — 패배해도 시간점수가 쌓인다.
이를 **예산 소모 모델** 로 교체한다: 시간·스트레스 예산을 만점으로 두고 소모한 만큼 깎는다.
여기에 처치 성과(킬점수)를 더한다.

## 산식

```
시간점수     = 남은시간ms × 초당점수 / 1000      // 패배 시 0
스트레스점수  = max(0, 한계 − 누적) × 점당점수
킬점수       = Σ 실제 처치한 적의 killScore
총점         = 시간 + 스트레스 + 킬
```

- `누적 스트레스 = _goalReachedCount + _leakAllowancePenalty` (유출 + 몽마의 계약 선불)
- `한계 = deck.defeatGoalReachedCount` **원본값** (계약 차감 후 값이 아니다 — 차감분은 누적 쪽에 있다)

| 예산 | 만점 | 근거 |
|---|---|---|
| 시간 | 18,000 | 180초 × 100. **실질 상한은 아래 "도달 가능 범위" 참조** |
| 스트레스 | 9,000 | 한계 × 점당점수 (현재 10 × 900) |
| 킬 | **가변** | 스폰 구성에서 런타임 누적 (계약 7). 상수가 아니다 |

> **킬 예산은 밸런스가 바뀔 때마다 움직인다.** 참고로 2026-07-21 기준 74기(잡몹 72 + 보스 2)
> = 11,200 이지만, 이 숫자에 의존하는 코드나 테스트를 만들지 말 것. 실제로 `wave-pattern`
> 밸런싱이 들어오면서 63기/10,300 → 72기/11,200 으로 바뀌었다.
>
> **한계와 점당점수는 곱해서 예산이므로 짝으로 움직인다** — 한계를 바꾸면 점당점수도 조정할 것.

**킬 만점을 상수로 박지 않는다.** 밸런스 튜닝은 물론이고 `waveSeed` 가 0이 되면 매판 랜덤이라
킬 총합이 크게 흔들린다(`waveCount` 가 커지면 보스가 3기가 되기도 한다).
스폰 시 `killScore` 총합을 런타임 누적한다.

## 유출은 두 축을 동시에 깎는다

**유출한 적은 킬점수를 남기지 않는다.** `EnemyKilledEvent.cs:7-8` 이 명시한다 —
*"Enemies that reach the goal go through a separate path (UnitLifecycleSystem) and do NOT emit this."*
유출 경로(`UnitLifecycleSystem.cs:56-61`)는 `DeadTag` 없이 `ecb.DestroyEntity` 로 직행하므로
`DamageApplicationSystem.cs:199` 의 `newHp <= 0` 분기에 도달하지 않는다.

| 유출 대상 | 스트레스 | 킬 | 합 |
|---|---|---|---|
| 잡몹 | −900 | −100 | **−1,000** |
| 보스 | −900 | −2,000 | **−2,900** |

의도된 결과다. 유출은 실패이고, 보스를 흘리는 쪽이 더 아파야 한다.
**따라서 킬점수는 승리자끼리도 변별력을 갖는다** (승리는 유출 `한계−1` 회까지 허용).

## 분기가 하나뿐인 이유

**패배 시 스트레스점수는 정확히 0이 된다.** 근거 3개가 맞물린다:

- 패배 조건 `G ≥ L − P` (`BattleBridge.cs:3669` + `:3630`) → 이항하면 `G + P ≥ L`
- 지불 게이트 `(L − P − G) − cost ≥ 1` (`:3647`) → 지불 후 항상 `G + P ≤ L − 1`
- 유출은 `_goalReachedCount++` 로 1씩만 증가 (`:3664`)

세 조건에서 패배 트리거 시점의 `G + P` 는 L 을 넘어설 수 없고 **정확히 L** 이다.
같은 불변식에서 **비패배 종료 시엔 항상 `G + P ≤ L − 1`** → 승리하면 스트레스점수 **최소 900** 이 보장된다.

`max(0, ...)` clamp 는 위 불변식상 불필요하지만, `defeatGoalReachedCount ≤ 0` 인 덱 오저작 한 건이
음수 총점을 만들 수 있으므로 방어적으로 둔다.

**버팀 승리(`victory_timeout`)의 시간점수도 자동으로 0이다** — `RemainingBattleSeconds()` 가
`Mathf.Max(0f, ...)` 로 clamp 되어 있고(`:3688`), 이 경로는 `0f` 를 명시 전달한다(`:3701`).

따라서 명시 분기는 **"패배면 시간점수 0"** 한 줄뿐이다.

| 종료 | 시간 | 스트레스 | 킬 |
|---|---|---|---|
| `victory` (전멸) | 남은 시간분 | 최소 900 보장 | 실제 처치분 (유출분 제외) |
| `victory_timeout` (버팀) | 0 — 자동 | 최소 900 보장 | 실제 처치분 |
| `defeat` (스트레스 한계) | 0 — **명시 분기** | 정확히 0 — 자동 | 실제 처치분 |

## 웨이브 스케줄 — 무엇이 고정이고 무엇이 아닌가

`WaveA.asset` 의 `waveSeed` 가 비0이라 `BattleBridge.cs:1543` 에서 고정 오버라이드로 쓰인다
→ **모든 플레이어가 동일 스케줄**을 받는다. 점수를 서로 비교하려면 이게 유일한 필수 조건이다.

반대로 **웨이브 수량·간격·적 구성은 언제든 바뀐다.** 점수 시스템은 여기에 의존하지 않는다 —
킬 예산은 실제 스폰에서 런타임 누적하고(계약 7), 시간축은 클리어 시각만 본다.

`WaveKillBudgetPinTests` 가 지키는 것은 **구조 불변식뿐**이다:

- `waveSeed` 비0 (결정론)
- 같은 시드 → 같은 결과 (생성기에 비결정 요소 없음)
- 보스가 `bossWaveInterval` 주기에만 편성됨
- 모든 유닛이 `killScore > 0` (0이면 킬축이 죽는다)
- 마지막 스폰이 제한시간 안에 있음 (아니면 정상 전멸 승리가 불가능)

수량 배열·킬 예산·마지막 스폰 시각을 못박던 초기 버전은 폐기했다. 밸런스가 바뀔 때마다
깨지는데 방어 가치가 없었다.

## 도달 가능 범위 (시간축)

시간점수는 당기기(`ForceNextWave`, `:1646`) 사용량에 따라 10배 넘게 갈린다.

| 플레이 | 클리어 시각 | 시간점수 |
|---|---|---|
| 당기기 없음 | 마지막 스폰(현재 ~166s) + 소탕 | **1,000 내외** |
| 최대 압축 (이론) | ~18s (전 웨이브 즉시 소환 + 소탕) | **~16,000** |

**이 비중을 수용한다 (2026-07-20 결정).** 과도한 압축은 전 웨이브 동시 소환이 되고, 그러면 유출이 터져
스트레스(−900/회)와 킬(−100~−2,000/회)이 동시에 깎인다. 즉 "버틸 수 있는 만큼만 당긴다"는
리스크 조절이 자연 억제로 작동하며, 그 조절이 이 게임의 실력 표현이다.
따라서 위 16,200 은 다운사이드 없음을 가정한 **천장**이지 달성 가능한 값이 아니다.

보상 대상이 당기기라는 **행동**이 아니라 클리어 시각이라는 **결과**이므로 계약 8에 저촉되지 않는다.

## feature-wide 계약

1. 점수 계산은 순수 static `ScoreMath` 에만 존재한다. `int` 만 쓰고 `float` 을 쓰지 않는다.
2. 시간은 `ScoreMath` 진입 전에 ms 정수로 확정된다. 부동소수 시각이 산식 내부로 들어가지 않는다.
3. 승패에 따른 점수 규칙(패배 시 시간점수 0)도 `ScoreMath` 안에 둔다 — Bridge 에 흩지 않아야 테스트로 고정된다.
4. 초당점수·점당점수는 `ScoreRulesData` SO 에서 온다 (제약 6). `ScoreMath` 는 상수를 갖지 않는다.
5. 티어 enum 을 신설하지 않는다. 킬 가치는 `AttackUnitData.killScore` 유닛별 직접 값이다 (제약 8).
6. 킬점수는 `EnemyKilledEvent` 에 **enqueue 시점 베이크**로 실린다 — 드레인 시점엔 엔티티가 파괴돼 있다 (`awakeningReward` 선례, `EnemyKilledEvent.cs:18`).
7. 킬 만점을 상수로 박지 않는다. 스폰 구성에 의존하므로 런타임 누적한다.
8. 스트레스 한계는 `deck.defeatGoalReachedCount` **원본값**이다. `EffectiveLeakLimit()`(계약 차감 후)이 아니다.
9. **킬 누적 변수는 `_battleClock` 이 0이 되는 모든 지점에서 함께 0이 된다.** 현재 `_goalReachedCount`/`_leakAllowancePenalty` 는 `BeginPlacement()`(`:1104-1105`) 1곳, `_battleClock` 은 `StartBattle()`(`:1151`)·`StopBattle()`(`:1399`) 2곳으로 **비대칭**이다. 킬 누적을 `BeginPlacement` 에만 두면 같은 방식으로 발산한다.
10. 당기기 자체에 점수를 주지 않는다. 무결점 보너스·콤보 배율을 만들지 않는다.
11. 동점 타이브레이커는 **제출 시각 선착순** 단일 기준이다.
12. 라이브 HUD 점수(`ScoreHudView`, 처치당 +10)는 **표시 전용으로 존치**한다. 이번 스펙에서 통합하지 않는다.

## 구현 메모

- `ScoreMath.Evaluate(...)` 단일 진입점이 세 축 + 총점을 담은 struct 를 반환한다.
- **`long` 중간값은 불필요하다.** 최악 180,000ms × 100 = 18,000,000 이고, int 오버플로 임계는 초당점수 11,930 이다. SO 값이 그 근처에 갈 일이 없다.
- 절삭 손실은 초당 100 기준 10ms 미만이다 (`ms × 100 / 1000` = `ms / 10`).
- 남은 시간의 출처는 기존 `RemainingBattleSeconds()` 다 (`:3688`, 이미 `ResultScreen` 으로 넘어가는 값).
- 새 asmdef 를 만들지 않는다. `Wassup.Runtime` 안에서 기존 pure static 컨벤션(`ModifierMath`)을 따른다.
- 총점 규모가 1,800 → 20,000~35,000 대로 바뀐다. 리더보드 폴백은 점수에 비례한 더미를 만들지 않으므로(대기 상태 표시) 영향받지 않는다.

## 결정 기록

- **당기기 무제한 현행 유지** (2026-07-20). 쿨다운·동시 개수 제한을 넣지 않는다. 근거는 "도달 가능 범위" 절.
- **몽마의 계약 재지불 현행 유지** (2026-07-20). 호스트 사망 시 카드가 손패로 복귀하지만(`DreamcatcherHandController.cs:250`) 차감은 비가역이므로, 재부착마다 다시 지불한다. 한계 10 기준 최대 9회 재부착 → 스트레스 8,100 소각이 가능하다. 의도된 비용이다.

## 열린 항목

- **유출 한계 10 은 근거 없는 시작값이다.** 적 70여기 중 10기 유출이 적정한지는 실제 플레이 유출률 측정이 필요하다. unit 5 를 분리한 이유이며, SO 필드 하나라 조정이 싸다. **되돌리면 스트레스 예산이 27,000 이 되어 총점 규모가 48% 튄다** — 되돌릴 때 점당점수를 함께 조정할 것.
- **계약의 점수 손실이 HUD 에 경고되지 않는다.** 유출 한계 카운터만 보이고 "이 지불이 900점"이라는 표시가 없다. 별도 UI 과제.

## 후속 후보 (범위 밖)

- **점수 재검증 / 무효 플래그** — 서버가 배틀로그의 점수 입력값으로 재계산해 클라이언트 제출값과 대조. 결정론적 재시뮬은 고정 타임스텝 도입이 선결이라 별도 대형 spec.
- **라이브 HUD 점수 ↔ 최종 점수 통합** — `docs/spec/score-hud/4_handoff_summary.md:40` 에서 이관된 기존 후보.
- **정예 등급 도입** — 현재 잡몹 9종 + 보스 1종뿐이라 중간 등급이 없다. 밸런스 변경이라 별도 spec.
- **계약 지불의 점수 손실 HUD 경고** — 위 열린 항목.
